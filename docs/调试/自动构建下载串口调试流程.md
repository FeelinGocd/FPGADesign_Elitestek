# GamingPlayUnit 自动构建、下载与串口调试流程

本文记录当前已经在本机验证过的 RISC-V 固件调试流程，适用于：

```text
project/GamingPlayUnit/embedded_sw/SoC_RISCV32/software/standalone/GamingPlayUnit
```

## 1. 构建环境

Efinity 工具链位于：

```text
E:\FPGA\Efinity\EfinityRISCV
```

PowerShell 中先加入工具链路径：

```powershell
$env:PATH = 'E:\FPGA\Efinity\EfinityRISCV\toolchain\bin;E:\FPGA\Efinity\EfinityRISCV\build_tools\bin;' + $env:PATH
```

进入固件目录后执行：

```powershell
make.exe -j1 BSP_PATH=../../../bsp/efinix/EfxSapphireSoc GAME_PROFILE=1 GAME_BULLET_TINT=1
```

强制全量编译：

```powershell
make.exe clean BSP_PATH=../../../bsp/efinix/EfxSapphireSoc
make.exe -j1 BSP_PATH=../../../bsp/efinix/EfxSapphireSoc GAME_PROFILE=1 GAME_BULLET_TINT=1
```

输出文件位于：

```text
build/GamingPlayUnit.elf
build/GamingPlayUnit.bin
build/GamingPlayUnit.hex
```

## 2. 编译开关

`GAME_BULLET_TINT=1` 保留敌方弹幕红色 Tint；设为 `0` 可进行 Alpha-only 性能对比：

```powershell
make.exe -B -j1 BSP_PATH=../../../bsp/efinix/EfxSapphireSoc GAME_BULLET_TINT=0
```

测试结束后恢复为 `1`。`GAME_PROFILE=1` 保留串口性能统计。只改命令行宏时使用 `-B` 全量重编译，否则 Make 可能沿用上次生成的目标文件。背景恢复的 A/B 开关为 `GAME_BG_DIRECT_MAX_CELLS`（默认 24）、`DIRTY_LIST_MAX`（默认 128）和 `GAME_BG_MERGE_MAX_CLEAN_CELLS`（默认 2）；`PERF_TEST_MODE=3` 仅用于短时关闭背景恢复的性能定位。

## 3. Run 模式下载

当前板卡使用 TI 版本 FTDI 配置：

```text
bsp/efinix/EfxSapphireSoc/openocd/ftdi_ti.cfg
bsp/efinix/EfxSapphireSoc/openocd/debug_ti.cfg
```

本工程的 ELF 执行段和入口均在片上 RAM `0x1000`。当前已验证的 Run 流程是把 `GamingPlayUnit.bin` 装入 RAM，然后显式 `resume 0x1000`。`flash_ti.cfg` 的 `program ELF` 会写 SPI Flash；即使打印 `Programming Finished`，也不代表正在运行的 RAM 程序已更新。串口监听先启动，再执行 OpenOCD，以捕获启动日志。

先打开串口：

```powershell
python tools/GamePad/game_pad.py -p COM5
```

再在另一个终端进入固件目录，执行下载：

```powershell
$fw = 'E:\project\FPGA_Project\FPGA_Elitestek\FPGADesign_Elitestek\project\GamingPlayUnit\embedded_sw\SoC_RISCV32\software\standalone\GamingPlayUnit'
Set-Location $fw
$env:PATH = 'E:\FPGA\Efinity\EfinityRISCV\openocd\bin;' + $env:PATH
openocd.exe -s "E:\project\FPGA_Project\FPGA_Elitestek\FPGADesign_Elitestek\project\GamingPlayUnit\embedded_sw\SoC_RISCV32\bsp\efinix\EfxSapphireSoc\openocd" -f ftdi_ti.cfg -f debug_ti.cfg -c "soft_reset_halt" -c "load_image E:/project/FPGA_Project/FPGA_Elitestek/FPGADesign_Elitestek/project/GamingPlayUnit/embedded_sw/SoC_RISCV32/software/standalone/GamingPlayUnit/build/GamingPlayUnit.bin 0x1000 bin" -c "resume 0x1000" -c "shutdown"
```

重新烧录 FPGA 后，必须在 `load_image` 前执行 `soft_reset_halt`。2026-10-26 上板复测：省略该命令时 JTAG 显示下载成功、RAM 内容及外设 ID 可读，但 CPU 停在低地址且 COM5 无输出；加上该命令后正常启动。判断成功应以串口出现新版 `PERF TEST` / `PROBE` 为准。

成功标志：

```text
JTAG tap ... found: 0x10660a79
Target successfully examined.
78630 bytes written at address 0x00001000
downloaded 78630 bytes ...
PROBE 1s: ... restore=...(d/c=...)
```

这是 RAM Run 流程：`debug_ti.cfg` 初始化时先暂停 CPU，`load_image` 写 RAM，`resume` 从入口运行，OpenOCD 随后退出。字节数随构建变化；以 `bytes written` 和新版串口日志同时出现为成功依据。RAM 程序在掉电或重新加载 FPGA 配置后需要重新装入。

## 4. COM5 串口采集

板端串口参数为 `COM5 @ 115200`。交互工具：

```powershell
python tools/GamePad/game_pad.py -p COM5
```

只读采集：

```powershell
@'
import serial, time, sys
sys.stdout.reconfigure(encoding='utf-8', errors='replace')
s = serial.Serial('COM5', 115200, timeout=0.2)
t = time.time()
data = []
while time.time() - t < 10:
    data.append(s.read(4096))
s.close()
print(b''.join(data).decode('utf-8', 'replace'))
'@ | python -
```

出现 `PermissionError` 时，说明 COM5 已被其他程序占用；先关闭旧的 `game_pad.py`、串口监视器或 IDE 串口窗口，再按“先串口、后下载”的顺序重试。

## 5. 性能日志

```text
PROBE 1s: ... fps=..., cmd/max=..., restore=cells/cmds(d/c=direct_frames/copy_frames), bullet_draw=alpha/tint_enemy/tint_player
PROFILE 1s us avg/max: ... draw=... fence=... present=...
GPU 1s beats/frame: rd=... wr=... busy_cyc=... cmds=...
```

`restore` 和 `d/c` 是打印时**最后一帧**的值，不能当作整秒累计。`d=1` 表示该帧逐格直绘，`c=1` 表示该帧从 `FB_BG` 横向复制。当前 51 发及以上测试帧均为 `d/c=0/1`；无弹幕、脏格很少时可见 `1/0`。

当前默认配置基线约为：192 发弹幕 30～40 fps，112 发约 58 fps，51 发约 58～59 fps。

2026-10-26 同板 A/B：默认 `24/128` 时 192 发动态约 34 fps，51 发绘制约 3.4 ms；临时改为 `512/512` 强制直绘时，192 发动态约 31 fps，51 发绘制约 5.4 ms。直绘使 GPU 绘制命令从约 334 条/帧增至约 640 条/帧，因此保留默认配置。

后续同板定位：`PERF_TEST_MODE=3` 关闭背景恢复后，192 发达到约 58–60 fps，`draw/fence` 约 5.2/5.4 ms；正常恢复约 34 fps，`draw/fence` 约 9/7–9 ms。该模式画面会留下拖影，仅用于性能定位，完成后恢复 `PERF_TEST_MODE=2`。

横向恢复合并跨度 A/B：跨越 0 格约 31 fps，跨越 2 格约 34 fps，跨越 6 格约 32 fps；保留默认 2。缩小 A/B 子弹旧位置的标脏矩形虽减少脏格，192 发仍约 32 fps，且 `update` 增加约 0.2 ms，故已撤回。当前软件层面的简单参数调整未达到 60 fps；下一步应测量/优化 GPU 从背景帧缓存复制到显示缓冲的吞吐与同步。

已在 `GAME_PROFILE=1` 中加入 GPU 硬件 `rd_beats/wr_beats/busy_cyc` 每帧差值（第二次 `PROFILE` 起打印）。2026-10-26 重新烧录 FPGA 后，上板采集到：192 发、背景恢复开启时约 29–34 fps，GPU 读约 14–15.5 万 beat/帧、写约 14–15.6 万 beat/帧；关闭背景恢复时约 58–60 fps，GPU 读约 4.2 万 beat/帧、写约 4.5 万 beat/帧。每 beat 为 16 字节；可见背景恢复带来约 1.6–1.8 MB/帧的额外 DDR 读写。两组采样来自不同时间窗口，数值随弹幕位置和数量变化，不能当作严格同帧配对。

试过将每个 32×32 脏格的复制高度裁剪到精灵实际覆盖范围：正常恢复的 120 帧动态测试约从 34 升至 37 fps，GPU 读略降，但 RAM 占用增约 3 KB，未接近 60 fps，因此已撤回。

又试过只将 DDR 恢复格缩为 16×16（门、HUD 等仍使用 32×32 标脏）：读量降到约 13.3 万 beat/帧，但恢复命令约增至 134 条，120 帧仍约 37 fps；禁止跨空格合并后读量约 11.2 万 beat/帧、命令约 339 条，帧率仍在 29 fps 附近。该实验也已撤回。读量和命令数互相制约，单纯调整格子大小不足以实现 192 发 60 fps；后续需要验证更少命令的精确矩形恢复或 GPU 批量恢复能力，且每次 A/B 同时检查拖影。

2026-10-26 精确矩形 A/B：独立记录旧精灵像素矩形，按矩形面积和命令代价合并。全表逐对合并可把 GPU 读量降至约 9.8 万 beat/帧、恢复命令约 78 条，但 CPU 的 `draw` 升至约 17 ms，192 发约 29 fps。排序后线性合并将 `draw` 降回约 8 ms，但恢复命令约 172 条，GPU `fence` 升至约 11 ms，仍约 30 fps。限定附近候选的合并又使 `draw` 回到约 18 ms。该功能保留为默认关闭的 `GAME_BG_EXACT_RECT=0` 实验开关；正常构建仍走原恢复路径。

帧调度探针显示：192 发时，30/30 个游戏帧在提交显示前已跨过显示帧边界，平均约每个游戏帧跨两个显示中断。`IRQ_frame_isr()` 只清事件并计数；旧主循环每完成一次 `game_present()` 才更新游戏一次，因此渲染约 30 fps 时子弹移动和寿命也只更新约 30 次/秒。现在默认 `GAME_FIXED_UPDATE=1`：主循环按 16/17/17 ms 循环补跑逻辑，ISR 仍只提供边界信号；上板实测 192 发期间每秒约 60–61 次逻辑更新、显示约 29–32 帧。此改动修正游戏速度，不会单独提高显示帧率。显示基址必须在帧边界之前写好；在帧起始 ISR 内才写通常已赶不上当前帧。

## 6. 已知限制

- 通用 `ftdi.cfg` 找不到设备；当前板卡使用 `ftdi_ti.cfg`，其 JTAG ID 为 `0x10660a79`。
- 旧文档中的 `flash_ti.cfg` + `program ELF reset exit` 只证明 SPI Flash 写入；对当前 RAM 链接的固件，不可作为运行新版 C 代码的验证。
- OpenOCD 必须从固件目录启动，使配置脚本能找到上层的 `cpu0.yaml`；否则报 `cpuConfigFile /cpu0.yaml not found`。
- `http://127.0.0.1:3080/` 当前返回 `401 Unauthorized`，暂不纳入自动流程。
