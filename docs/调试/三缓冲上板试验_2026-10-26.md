# 三缓冲上板试验（2026-10-26）

## 地址

地址定义集中在 `game/framebuffer_layout.h`。C、D 各占 8 MiB；A 左、A 右、B 左、B 右各占 4 MiB；背景缓存占 `0x0A000000–0x0A7FFFFF`；第三帧占 `0x0A800000–0x0AFFFFFF`。全帧物理占用按旧的 5760 字节行距和 1440 行计算，为 8,294,400 字节，比 8 MiB 槽少 94,208 字节。预处理检查阻止槽重叠及地址越过 GPU 的 28 位窗口。

## 实现

`GAME_TRIPLE_BUFFER=1` 为默认配置，`=0` 可编译原双缓冲交帧路径。每块帧的旧精灵位置、HUD、道具池和地板状态各有独立记录。主循环只从“当前显示帧”和“待显示帧”以外选择绘制目标；GPU fence 完成后写显示基址，待下一次帧中断确认交接后才重用旧显示帧。ISR 仍只计数并清中断。房间切换和重开前先完成待显示帧交接。GAME OVER 自动重开也移至主循环处理。

## 实测

COM5 在下载前打开，OpenOCD 使用 `soft_reset_halt`、`load_image ... 0x1000 bin`、`resume 0x1000`。三缓冲固件成功完成三块帧的初始化，无 GPU timeout。192 发且背景恢复开启时，多个上板采样窗口为 52–56 fps，逻辑约 60 次/秒，最终构建 RAM 占用 103,568 / 126,976 字节（81.57%）。旧双缓冲同场景约 29–34 fps。弹量降到 112 发后为 58 fps。

串口日志：`verification/triple_20261026.log`、`verification/triple_final2_20261026.log`。后者记录到 GAME OVER 后 5 秒正常自动重开。自动方向键试验记录在 `verification/triple_room_20261026.log`，确认 game_pad 两字节协议可驱动角色移动且约 59 fps；该路径没有成功触发房间过门，所以房间切换的 HDMI 画面仍需人工查看。串口性能数字也不能证明画面没有残影或撕裂。

本次 192 发尚未达到 60 fps。满载时 `draw + fence + update` 接近或超过 16.7 ms，三缓冲消除了多余的帧边界等待后，后续仍需降低这部分实际工作量。

## 静态布局命令数对照

`1x1_001` 含 24 个石头、9 张网；`1x1_002` 含 28 个石头、12 个箱子、17 张网。原路径每帧提交这些静态物体，即使房间已清空。新增 `GAME_STATIC_CULL=1`：每块帧缓冲第一次绘制、房间切换或地板重建时提交全部静态物体；平时仅在脏格覆盖物体时重画。石头与当前动态物体相交时仍参与深度排序。`GAME_STATIC_CULL=0` 可用于对照。

用临时编译参数 `PERF_TEST_MODE=0 GAME_TEST_START_LAYOUT=2` 固定起始房为 `1x1_002`，无弹幕、不移动角色，上板对照：关闭裁剪时约 161 条命令/帧；启用后稳定约 43 条命令/帧、59 fps，绘制阶段约 4.7 ms。首次绘制仍会有一次完整提交。测试日志为 `verification/static_off.log`、`verification/static_fast_steady.log`。之后已恢复 `GAME_TEST_START_LAYOUT=-1 PERF_TEST_MODE=2` 编译并上板；192 弹首两段日志约 50–51 fps、350–357 条命令/帧，记录在 `verification/static_final_192.log`。静态布局裁剪解决的是清空后房间的冗余命令，未改变高弹幕阶段的瓶颈。角色穿过石头、切换房间时的画面仍需人工检查。

## 交互贴图闪烁与周期性卡顿

背景恢复在脏格超过 `GAME_BG_DIRECT_MAX_CELLS` 时，会跨过最多 `GAME_BG_MERGE_MAX_CLEAN_CELLS` 个干净格合并相邻复制段。静态物体原先只检查自己的格子是否标脏，合并复制可能擦掉未标脏的石头、箱子或蜘蛛网。本次把静态物体的重画判定扩展到可能被合并复制覆盖的横向格子；可选的矩形合并模式保守重画全部静态物体。固定 `1x1_002` 且移动角色的串口试验仍记录到 59 fps、每秒约 60 次逻辑更新，日志为 `verification/interact_move.log`；高弹幕复制路径已上板启动，日志为 `verification/interact_copy_stress.log`。串口无法验证具体像素，仍需观察 HDMI。

之前每秒同步打印 PROBE、PROFILE、IRQ、SIM、GPU 多行日志，测试窗口反复出现 `gap_ms` 最大 41–43 ms，平均帧率仍显示约 59。这种周期性帧间隔会让移动显得不流畅。正常构建现默认 `GAME_PROFILE=0 GAME_UART_TELEMETRY=0 PERF_TEST_MODE=0`，保留 HUD 实时数值，停用每秒串口性能输出和开局 192 弹。压测时可显式构建 `PERF_TEST_MODE=2 GAME_PROFILE=1`，此时遥测自动启用。安静版已重新上板，自检、初始化和串口 P 命令均通过，启动日志为 `verification/interact_quiet_retry.log`。用户随后目视确认贴图闪烁和移动卡顿均已修复。

## 192 弹瓶颈对照

固定空 `1x1_000` 起始房，`GAME_PROFILE=1 GAME_TEST_START_LAYOUT=0`，只改变一个编译开关。`draw` 进一步分成脏区等准备、渲染队列提交、排序和绘制命令执行三段；下面取开局仍有 192 弹的首个约 1 秒窗口。

| 配置 | FPS | draw / fence 平均 | draw 内部 prepare / submit / execute | 背景恢复 |
| --- | ---: | ---: | ---: | ---: |
| 恢复开、染色开（基线） | 52 | 10.8 / 7.0 ms | 2.0 / 0.38 / 8.4 ms | 406 格、71 命令 |
| 恢复关、染色开（诊断） | 61 | 6.5 / 4.4 ms | 1.8 / 0.37 / 4.3 ms | 0；画面有残影 |
| 恢复开、染色关（诊断） | 49 | 11.8 / 7.0 ms | 2.3 / 0.38 / 9.1 ms | 402 格、71 命令 |

原始日志依次为 `verification/ab_base.log`、`verification/ab_no_restore.log`、`verification/ab_no_tint.log`。基线与关闭恢复对照时，GPU 每帧读写各少约 9.8 万 beat（16 字节/beat，读写合计约少 3.1 MB）。这说明恢复旧弹位置的 DDR 搬运是当前主要成本；关闭实时染色没有收益，且会改变弹幕颜色。关闭恢复仅用于定位，不能交付。此前的 16×16 脏格和精确矩形合并试验已分别因命令数或 CPU 合并成本过高失败，见《自动构建下载串口调试流程》。下一步应优先试保守缩小子弹真实像素覆盖范围，逐一验证旋转后的 alpha 边界与残影；若收益不足，再评估硬件批量恢复。

### 透明边脏区试验

三张 32×32 弹图的非透明像素范围分别是 A `(4,4)..(28,29)`、B `(7,8)..(25,29)`、C `(3,6)..(31,27)`，右下角为开区间。已用图片 alpha 通道核对镜像与 90 度旋转。`GAME_BULLET_DIRTY_BOUNDS=1` 时，每块帧缓冲记录当次实际画出的弹种与朝向，下一次恢复旧弹位置时按保守包围盒标脏；默认仍为 0。

在同样的 192 弹空房压测中，第一版所有方向共用边界首秒约 55 FPS、恢复 369 格/70 命令，第二版按方向边界首秒约 54 FPS、恢复 375 格/70 命令；原基线约 52 FPS、406 格/71 命令。采样瞬间不同会影响格数，GPU 读量约从基线的 13.99 万 beat/帧降到 13.28–13.49 万 beat/帧，但未达到稳定 60 FPS。日志为 `verification/bullet_bounds_on.log` 和 `verification/bullet_bounds_axis.log`。试验版仍需 HDMI 目视检查是否有弹幕边缘残留，在确认前不作为默认配置。

用户目视确认按方向边界试验没有弹幕拖尾或闪烁，但体感仍偏低。该试验固件开启每秒同步性能日志，记录到每秒约 45–48 ms 的最长帧间隔；其“59 FPS”是平均值，无法代表每帧都平稳。由于边界方案只有约 2–3 FPS 的收益且仍未到 60，保持 `GAME_BULLET_DIRTY_BOUNDS=0` 默认关闭。已重新构建并上板安静的正常游戏版本（`GAME_PROFILE=0 PERF_TEST_MODE=0`），启动日志 `verification/bullet_bounds_restored.log`。用户正在对比无日志版本的实际移动观感。

## 弹幕上限与 Boss 运动

用户确认安静版的移动观感已恢复。继续在固定空 `1x1_000` 房做同场景对照：背景复制合并阈值从 2 改为 1 后，192 弹首秒仍为 52 FPS、第二秒 53 FPS，恢复命令从约 71 条增至 95 条，没有收益（`verification/merge1_192.log`）。因此保留阈值 2。

新增仅供压测使用的 `PERF_TEST_BULLETS` 编译参数。128 弹首秒 61 FPS、后续采样约 58 FPS；96 弹首秒 61 FPS、后续采样也约 58 FPS（`verification/bullets128_192layout.log`、`verification/bullets96_empty.log`）。后续窗口含每秒同步遥测，出现 42–49 ms 的帧间隔；这些 58 FPS 不能直接视为安静版的持续吞吐，但 Boss 动作与招式尚需预算，所以正式游戏先把弹池上限从 192 降到 96，敌弹在总活跃数达到 64 时停止生成，为玩家保留 32 槽。RAM 占用降至 97,392 / 126,976 字节（76.70%）。

Boss 运动启用幅度 96 像素、约 5.1 秒一周期的横向往返，正弦表做逐帧线性插值，进入战斗等待结束时从场地中心起步。原有招式表暂时沿用。正常安静版已按“先开 COM5，再下载 RAM 镜像”流程上板；最终日志 `verification/boss_motion_quiet_final.log` 显示 `INIT 7/7`，没有初始化错误。Boss 房中移动、招式数量和实际帧率尚需进入 Boss 房做实测与目视验证；空房压测不能代表 Boss 房负载。

## Boss 房直达调试

第一次人工进入 Boss 房的日志显示 `FIGHT: stage 1` 与 `ROOM: boss layout=7`，随后很快 Game Over，无法覆盖完整招式。按用户要求，改用原来的普通开局，在 `GAME_BOSS_DEBUG=1` 构建中加入 game_pad 的 **T** 键跳转 Boss 房，并让玩家免受伤害；正常构建默认 `GAME_BOSS_DEBUG=0`。T 键通过串口虚拟手柄 bit7 发送，按键上升沿只触发一次；跳转沿用房间的完整重建流程，落点在 Boss 房下方，避免与 Boss 初始位置重叠。需重新启动 `tools/GamePad/game_pad.py` 才会加载 T 键映射。

带性能日志的调试版已经按 T 做了 16 秒上板采集：成功打印 `DEBUG: jump to boss room`、`FIGHT: stage 1`、`ROOM: boss layout=7`，敌弹峰值达到 64 发，玩家仍为 3 血，未出现 Game Over。Boss 房多数窗口约 58 FPS，`gap_ms` 最大约 47–49 ms，主要受每秒同步性能日志影响；记录见 `verification/boss_jump_action.log`。之后已上板 **无性能日志** 的同一调试版，并再次通过串口 T 跳转到 Boss 房（`verification/boss_jump_quiet_action.log`）。HDMI 画面平滑度及 Boss 运动仍待目视确认。

为排除日志对帧节奏的干扰，调试版新增按需读取的 `stat` 命令。11 秒安静 Boss 战采样为 `frames=660 irq=660 irq_max=1 sim=660 gap_max=17 slow25=0 slow33=0 fence_max_us=3172`，见 `verification/boss_frame_diag.log`。这段采样没有漏显示中断，也没有大于 25 ms 的帧开始间隔；用户仍观察到右半屏弹幕密集时偶发视觉停顿、没有撕裂或残留。采样没有与目视停顿精确对齐，因此不能据此断言停顿来自子弹运动还是显示通路。下次目视停顿后立即执行 `stat`，同时区分是整幅画面还是仅弹幕停顿。

Boss 招式表与运动池现已分开：`g_boss_moves[]` 的第三列引用 `g_boss_motions[]`，运动池记录运动类型、幅度和周期。现有全部招式都引用编号 0（原横向往返），因此这一步不改变当前战斗行为。此结构改动已随自动负载诊断版编译并上板。之后可按招式设计对应移动，但切换不同轨迹时还需处理位置连续性，避免 Boss 瞬移。

## Boss 弹幕与滑动视角联合负载

用户观察到右半屏弹幕密集时偶发视觉停顿，HUD FPS 没有下降，也没有撕裂或残留。为检验“招式 + 滑动视角导致命令数突增”，加入可选 `GAME_BOSS_AUTO_DIAG=1`：每帧按“相机移动与否、敌我活跃弹数是否达到 32”归类，15 秒输出一次命令均值/峰值、脏格峰值、绘制和 GPU 等待峰值、最长帧间隔。输出后的三帧不纳入下一窗口，避免串口打印污染结果。正式构建默认关闭。自动手柄脚本 `verification/capture_boss_cam.py` 从 T 跳转 Boss 房开始，交替横向、纵向移动及停住；手柄状态每 50 ms 续发以免固件超时清键。

第一次自动脚本没有续发按键，移动视角样本为零，日志 `verification/boss_cam_auto.log` 只作静止基线。修正后 `verification/boss_cam_auto2.log` 的横向采样：密集弹幕、相机静止时 142–164 条命令/帧，移动时 183–199 条命令/帧；相机移动窗口内 GPU 等待峰值最高约 4.6 ms、帧开始间隔最多 17 ms，`slow25=0`。`verification/boss_cam_vertical.log` 中纵向移动窗口达到 209 条命令/帧、峰值 214，脏格峰值 347、GPU 等待峰值约 4.9 ms、帧开始间隔最多 17 ms，仍为 `slow25=0`。这些数据证实视角滑动增加负载，但覆盖到的窗口没有因命令数峰值漏掉显示帧；尚不能从串口数字判断用户看到的局部视觉停顿原因。

试验后已编译并上板安静的 Boss 调试版（`GAME_BOSS_DEBUG=1 GAME_PROFILE=0 GAME_UART_TELEMETRY=0 GAME_BOSS_AUTO_DIAG=0`），保留 T 直达与玩家无敌，关闭定时采样输出；RAM 占用 96,864 / 126,976 字节（76.29%）。先开 COM5 再下载，启动日志 `verification/boss_cam_quiet_restore.log` 已确认 `INIT 7/7`。

后续又在自动分组统计中加入每帧逻辑更新次数，以检验“平均 60 次/秒、实际逐帧 0/2 次交替”的可能。`verification/boss_simsteps.log` 的两段密集弹幕采样中，静止/移动视角组的 `sim0/2` 均为 `0/0`，最长帧间隔均为 17 ms。因此这段 Boss 场景没有出现逻辑隔帧停住再追赶的节奏。仍需区分局部弹幕相对相机的运动观感与显示通路问题。

用户决定暂缓该视觉停顿的优化，继续 Boss 内容。移动池现包含横向往返、回中心、左定点、右定点、纵向轻漂五种目标；`g_boss_moves[]` 的第三列按招式引用它们。切换目标时每个逻辑步的位移由对应池项的 `speed` 限制，避免招式切换瞬移。自动 T 直达版追踪日志 `verification/boss_motion_pool.log` 覆盖了 0–13 全部招式并回到 0，左/右/纵向动作均进入，未出现 `BOSS MOVE ERROR`。随后已关闭追踪并重新上板安静调试版：`GAME_BOSS_DEBUG=1 GAME_PROFILE=0 GAME_UART_TELEMETRY=0 GAME_BOSS_MOTION_TRACE=0`，RAM 使用 97,184 / 126,976 字节（76.54%）；启动日志 `verification/boss_motion_pool_quiet.log` 已确认 `INIT 7/7`。HDMI 上的招式手感与公平性仍需目视体验。

## 招式负载与双螺旋截断

为检查视觉停顿是否集中在某招，增加可选 `GAME_BOSS_SKILL_DIAG=1`：整个 14 招循环期间按招式累计命令、活跃弹数、绘制和 GPU 等待峰值、长帧，以及敌弹生成被池容量拒绝的次数；循环结束才统一输出，避免采样期间持续串口打印。静止视角对照日志为 `verification/boss_skill_reject.log`。编号 2、8、12 达到 64 发上限，但每招最长帧间隔仍为 17–18 ms、`slow25=0`；编号 8「双螺旋」有 **64 次生成请求被拒绝**，编号 2 有 3 次，其余为 0。原双螺旋每轮 8 个方向又发反向双弹，8 轮共尝试 128 发，池满后招式仍前进，因此可出现弹流缺口。

只调整编号 8 的图案参数为每轮 4 个方向、反向双弹、间隔 5 帧、6 轮，共 48 发；保留双臂和接近原来的播放时长。复测 `verification/boss_skill_spiral_fix.log` 中编号 8 的拒绝数从 64 降到 **0**、活跃弹峰值为 48、最长帧间隔 17 ms。编号 2 仍有 3 次、编号 12 本轮有 1 次拒绝，暂未调整。该数据证明修复了双螺旋的容量截断，但不能单凭串口统计断言它就是用户所见的视觉停顿。

已关闭招式诊断，重新编译并下载安静的 Boss 调试版（`GAME_BOSS_DEBUG=1 GAME_PROFILE=0 GAME_UART_TELEMETRY=0 GAME_BOSS_SKILL_DIAG=0`）。RAM 占用 97,184 / 126,976 字节（76.54%）。`verification/boss_spiral_quiet.log` 确认 `INIT 7/7`、T 跳转和进入 Boss 房。

## Boss 房 1×1 视角对照（2026-10-26）

### 256 槽、保留半透明的绘制裁剪

A 型弹幕素材为 32×32，但非零 alpha 只在原图 `[4,28)×[4,29)` 内。`GAME_BULLET_ALPHA_CROP=1` 使敌弹 GPU 绘制只覆盖 24×25 像素；源 PRAM 地址按原素材跨距偏移 4 行和 4 像素，目标坐标偏移 `(4,4)`。四个方向按硬件翻转/转置规则逐像素与原素材比对，通过 `verification/test_bullet_crop.py`；碰撞和旧帧脏区仍保留原 32×32 范围。继续使用 alpha tint，因此弹幕中心的半透明仍由硬件混合。

同样的合成压测中，原全尺寸 alpha 256 发为 2365 ms/120 帧，约 50.7 FPS；裁剪后为 2088 ms/120 帧，约 57.5 FPS，仍不满足持续 60。裁剪版 224 发、240 发分别连续三个 120 帧窗口通过，间隔峰值 17–18 ms、无渲染丢弃，日志在 `verification/boss_sweep_alpha_crop_repeat_256_20261027.log`。打开 `GAME_BULLET_DIRTY_BOUNDS=1` 后脏区恢复命令碎片化，256 发为 2115 ms；跨空格合并从 2 格缩至 1 格后为 2083 ms，均未使 256 发达标。关闭实时染色但保留裁剪，256 发为 2091 ms，表明省掉 tint 命令对当前瓶颈帮助很小。相应日志分别为 `verification/boss_sweep_alpha_crop_dirty_256_20261027.log`、`boss_sweep_alpha_crop_merge1_256_20261027.log`、`boss_sweep_alpha_notint_crop_256_20261027.log`。

正式默认弹池现改为 **256 个总槽位**，其中给玩家保留 32 槽，敌弹生成阈值为总活跃数 224；默认启用 alpha 绘制裁剪，保留背景合并 2 格并关闭脏区边界收缩。Boss 调试正常版 RAM 105,376 / 126,976 B（82.99%），镜像为 `verification/boss_normal_256_alpha_crop_20261027.bin`。按先开 COM5 再下载的流程已上板；`verification/boss_normal_256_alpha_crop_boot_20261027.log` 记录 `INIT 7/7`、T 跳转和 Boss 开战。无调试参数的默认构建也编译通过，RAM 105,952 / 126,976 B（83.44%），镜像为 `verification/game_release_256_alpha_crop_20261027.bin`。实际 Boss 战的画面、PAD 移动和 FPS 仍需目视确认；合成 240 发通过不能替代该验证。

### 真实 Boss 的密集弹幕技能

原六圈技能每圈 16 发、总计 96 发，无法在实际 Boss 流程中验证新弹池。新增 `DENSE_RINGS`：Boss 在中心发射七圈，每圈 32 发、相邻圈间隔 8 帧，角度逐圈错开 1 格，沿用减速再加速的 `MOTION_PULSE`。它排在 Boss 招式表第一项，开场无上一招残留，理论上正好填满 224 个敌弹名额，并始终给玩家预留 32 槽。原六圈技能仍保留。

诊断版上板日志 `verification/boss_dense_256_framediag_20261027.log`：最后一圈后 `enemy=224 total=224 rejected=0`；随后的真实 Boss 战 120 帧为 2003 ms，最长帧间隔 17 ms，超时帧 0，敌弹最低 220 发，命令均值/峰值 258/288。这个测量覆盖静止视角，仍需 PAD 移动目视检查。已上板关闭诊断输出的 Boss 调试版 `verification/boss_dense_256_quiet_20261027.bin`，启动日志 `verification/boss_dense_256_quiet_boot_20261027.log` 确认 `INIT 7/7`、T 跳转及开战，COM5 已释放。无调试参数的正式默认构建也通过，镜像为 `verification/game_release_256_dense_20261027.bin`，RAM 105,952 / 126,976 B（83.44%）。
