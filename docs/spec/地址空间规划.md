## 1. 三条硬约束

| # | 约束 | 出处 / 后果 |
|---|---|---|
| 1 | **所有 DDR 地址必须 < `0x1000_0000`（256 MB）** | `Axi_Mux` 地址 32 位 → DDR3 从口 28 位，高 4 位被丢弃，超出会回卷 |
| 2 | **一笔 AXI 突发不得跨 4 KB 边界** | AXI4 协议硬规矩，违反则从机行为未定义 |
| 3 | **CPU 写完的内存，在别人读它之前必须刷 D-cache** | CPU 有 4 KB 1-way D-cache（64 B/行），别的设备看不见它 |

按 `README.md` 的五项：Framebuffer A/B、贴图区、命令队列、堆栈。

| 区域 | 起始 | 结束 | 大小 | 写者 | 读者 |
|---|---|---|---|---|---|
| 保留空洞 | `0x0000_0000` | `0x0000_0FFF` | 4 KB | — | — |
| **CPU 程序/数据/栈** | `0x0000_1000` | `0x0001_FFFF` | 124 KB ✅ | CPU | CPU |
| **堆 / 栈扩展** | `0x0002_0000` | `0x001F_FFFF` | 1.875 MB | CPU | CPU |

>
> **注 3（2026-09-16 已重排）**：帧缓冲改为 **RGB888（3 字节/像素）** 后每帧只需 **约 6 MB**，

## 4. 帧缓冲布局

### 4.1 行跨距取 5760（= 行宽，不补齐）

1920 像素 × **3 字节**（RGB888）= **5760 字节/行**。

> ⚠️ **本节已按 RGB888 重写**。旧版按 XRGB8888（7680 字节/行、跨距补到 8192）编写，已作废。

**5760 是天然最优解**，因为三个整除条件同时成立：

| 性质 | 是否满足 | 说明 |
|---|---|---|
| 被 16（128bit = 一拍）整除 | ✅ 5760 = 16 × **360** | 一行正好 360 拍，无零头 |
| 被 3（1 像素）整除 | ✅ 5760 = 3 × 1920 | 行首永远是"像素 0" |
| 行首**拍相位** | ✅ 恒为 0 | 每行都从一拍的开头开始 |
| 行首**像素相位** | ✅ 恒为 0 | 每行第一个像素都从字节 0 开始 |
| 内存浪费 | ✅ **0** | 跨距 = 行宽，整帧是一整块连续数组 |

**含义：整帧就是一个"每行 360 拍"的连续数组，行与行之间没有任何空隙。** 🔧

```
第 y 行第 x 个像素 = 帧缓冲基址 + y × 5760 + x × 3
第 y 行的第 n 拍   = 帧缓冲基址 + y × 5760 + n × 16      (n = 0..359)
```

**代价**：行首地址不是 4 KB 的整数倍，4 KB 边界在行内的位置逐行漂移 🔧。
每行 5760 字节 → 最多跨 2 个 4 KB 块 → **每行 2 笔突发**（切点位置由读出器按行计算）。
若强行让行首对齐 4 KB，跨距要补到 8192，**每行浪费 2432 字节（+42%）** —— 不值得。

### 4.2 参数表（1080p，RGB888）

| 项 | 值 |
|---|---|
| 分辨率 | 1920 × 1080 ✅ |
| 每像素 | **3 字节（RGB888）** 🔧 |
| 行有效字节 | **5760** |
| 行跨距 | **5760**（= 行宽，不补齐） 🔧 |
| 每行拍数（128 位总线） | 5760 / 16 = **360 拍**（> 256 → 每行拆 2 笔） |
| 每帧字节 | 5760 × 1080 = **6,220,800 B（5.93 MB）** |
| 每帧分配 | 建议 **6 MB**（1 MB 对齐）⚠️ 待重排分区表 |
| 双帧合计 | **约 11.9 MB** |

### 4.3 640×480 调试模式

| 项 | 值 |
|---|---|
| 行有效字节 | 640 × 3 = **1920** |
| 每行拍数 | 1920 / 16 = **120 拍**（< 256 → **一行一笔**） |
| 每帧字节 | 1920 × 480 = **921,600 B（0.88 MB）** |

### 4.4 3 字节/像素带来的一个实现要点

128 bit = 16 字节，而 16 ÷ 3 = **5 个整像素 + 1 字节零头** →
从 AXI 读回来的一拍里，**像素是错位的**，需要字节级拼接才能切出一个一个 RGB888 像素。

**好消息**：因为 5760 和 1920 都能被 16 整除，**每行都从相位 0 开始，行与行之间不漂移**，
拼接的相位模式是固定循环的（每 3 拍 = 48 字节 = 16 个像素为一个循环）。

**另一个好处**：HDMI 输入就是 24 位 RGB，linebuffer 读出来**直接就能用**，不需要格式转换。

## 5. 缓存一致性（必须遵守）

### 5.1 问题

CPU 有 **4 KB 1-way D-cache（64 B/行）**，且 **没有 MMU**（`SYSTEM_CORES_0_MMU = 0`），
所以**不能靠页表把某段标成不可缓存**。

```
CPU 写 Framebuffer（软渲那部分）
   → 写停在 D-cache 里，没落到 DDR
显示读出器从 DDR 读
   → 屏幕上这部分不更新
```

注意方向：**不是"谁读到了旧数据"，而是"CPU 写的像素根本没到 DDR，而屏幕是从 DDR 读的"。**

### 5.2 解法：通知别人之前刷 cache

BSP 里已有现成实现（`app/lwip/user/arch/ethernetif.c:73`）：

```c
void flush_data_cache(){
    asm(".word(0x500F)");   // VexRiscv 自定义指令：刷 D-cache
}
```

| # | 场合 | 时机 |
|---|---|---|
| 1 | CPU 写 Framebuffer | 翻页（换 front 指针）之前 |
| 2 | CPU 装载贴图/素材 | 启动加速器之前 |
| 3 | CPU 写命令队列 | 写"启动"寄存器之前 |

### 5.3 反方向

加速器写、CPU 读 —— 本设计下 CPU 不需要读加速器写的区域，不用管。
若将来要读，读之前同样要刷。

## 6. 存储分层（四级）

| 层 | 器件 | 容量 | 来源 | 掉电 |
|---|---|---|---|---|
| **L1** 片上 BRAM | Ti60F225 内置 | **256 块 × 10 Kbit = 320 KB** ✅ | `project.res.csv` / 芯片手册 | 丢 |
| **L2** 片上小 RAM | SoC 内部 | bootloader 4 KB + OCR 8 KB ✅ | `soc.h:50` | 丢 |
| **L3** DDR3 | 板载 x16 DDR3 | **256 MB**（28 位地址封顶）✅ | `ddr3_parameter.vh` `AXI_ADDR_WIDTH=28` | 丢 |
| **L4** SPI Flash | GD25LQ64 | **8 MB** ✅ | 开发板说明书 §七 | **保存** |

> ⚠️ **常见笔误**：板载 Flash 是 **8 MB**（GD25LQ64 的 64 是 **64 Mbit**），不是 64 KB。

### 6.1 各层的性格（决定数据怎么分）

| 层 | 带宽 | 随机访问 | 定位 |
|---|---|---|---|
| **BRAM** | 极高（多端口，100 MHz 下单口 128 bit/拍） | ✅ 单周期 | **热点数据** |
| **DDR3** | 1.6 GB/s 理论，**实际 1.0~1.2 GB/s（读写共享）** | ⚠️ 几十拍延迟 | **大容量工作区** |
| **Flash** | 串行，几十 MB/s 级 | ❌ 需发命令+地址+dummy | **只做仓库，开机搬一次** |

### 6.2 BRAM 现状（256 块）✅

| 用途 | 块数 |
|---|---|
| **SoC（RISC-V）** | **43** |
| ├ DDR 跨时钟 FIFO | 17 |
| ├ CPU 的 I-cache / D-cache | 12 |
| └ 命令/响应队列 + bootloader RAM | 14 |
| **DDR3 控制器** | **22** |
| **`Axi_Mux`** | **0**（互联几乎不要钱：216 LUT / 37 FF） |
| **已用合计** | **65（25%）** |
| **剩余可用** | **191 块 ≈ 239 KB** |

**191 块能放多少 tile：**

| tile 格式 | 一个占 | 能放 |
|---|---|---|
| 64×64 ARGB8888 | 16 KB | 约 **14** 个 |
| 64×64 RGB565 | 8 KB | 约 **27** 个 |
| **64×64 索引色（8bpp）** | **4 KB** | **约 47 个** |

> 索引色见 §8。另外 linebuffer 还要占 9~12 块。

### 6.3 数据放哪：三条判据 🔧

| 判据 | 放哪 |
|---|---|
| **小而热**：每帧被复用很多次 | **BRAM** |
| **大而冷**：尺寸大，或一帧只读一次 | **DDR**（开机从 Flash 搬） |
| **要掉电保存** | **Flash** |

**Flash 不能当运行时存储用**：SPI 是串行接口、没有随机访问，读一个像素要先发命令+地址+dummy。
所以 Flash 只在**开机时搬一次**到 DDR，运行时不碰。

### 6.4 Flash 布局 ⚠️ 待确认

```
前段   FPGA bitstream（实测 1.83~2.36 MB，建议预留 4 MB）
后段   用户素材（约 4 MB）
```

> ⚠️ 需先查 Efinity Programmer 里 bitstream 的**烧录起始地址与长度**，别把素材区压在 bitstream 上。

## 7. 带宽预算（本工程真正的瓶颈）

### 7.1 两侧理论带宽恰好配平 ✅

| 侧 | 算法 | 结果 |
|---|---|---|
| **AXI 侧** | 128 bit × 100 MHz | **1.6 GB/s** |
| **DDR3 侧** | x16 × 800 MT/s（tCK 2500 ps → CK 400 MHz → DDR 800 MT/s） | **1.6 GB/s** |

> ⚠️ **关键事实：DDR 颗粒只有一条 DQ 总线，读写不能同时进行。**
> 所以 **1.6 GB/s 是读写共享的总量，不是各 1.6**。
> AXI/MUX 层面读写是两条独立通道（可以同时跑），但到 DDR 面前要排队，
> 而且**读写换向有开销**（`tWTR` 等）。
> 实际可用按 65~75% 估：**约 1.0~1.2 GB/s（读写合计）** 🔧

### 7.2 显示读出需求（RGB888）

| | 640×480@60 | 1920×1080@60 |
|---|---|---|
| 每行字节 / 拍数 | 1920 B / **120 拍** | 5760 B / **360 拍** |
| 行周期 | 31.78 µs（3178 拍） | 14.81 µs（1481 拍） |
| **读出速率** | **55 MB/s** | **373 MB/s** |
| 占理论 1.6 GB/s | 3.5% | **23.3%** |
| 占实际 1.0 GB/s | 5.5% | **37%** |

> **关键结论：显示只需要占用读通道约 1/4 的时间**（1080p）。
> 因此"单 outstanding"带来的笔间空隙（几十拍）**完全不影响刷新** —— 余量 3 倍以上。

### 7.3 并发预算（1080p，加速器画半屏）

| 流量 | MB/s |
|---|---|
| 显示读（整帧） | 373 |
| CPU 写半屏（按 60fps 上限估） | 187 |
| 加速器写半屏 | 187 |
| 加速器读贴图（**有 tile 复用 / 片上缓存**） | **~20** |
| 加速器读贴图（**无复用，逐像素 1:1 / 大块 Block Copy**） | **~249** |
| **合计（有复用）** | **~767 → 占实际 1.0 GB/s 的 77%** |
| **合计（无复用）** | **~996 → 99%，压线** |

**结论：**
- **640×480@60：非常宽松**（约 15%）。
- **1080p@60：取决于贴图复用率。**
  - 高频 tile 驻留 BRAM / 片上缓存 → **77%，可行**
  - 逐像素从 DDR 读 → **99%，压线**
- 所以 **"高频 tile 放 BRAM"不是可选优化，而是 1080p 能否成立的前提** 🔧

### 7.4 撕裂与带宽无关

| 现象 | 长什么样 | **真正的原因** | 解法 |
|---|---|---|---|
| **撕裂** | 画面上下是不同帧，中间一条错位横线 | **显示正在读的缓冲被人写了** | **双缓冲 + 只在帧边界（vblank）翻页** |

> **带宽再紧张，只要读写的是两块不同缓冲，就不会撕裂；**
> **带宽再宽松，只要读写同一块缓冲，照样撕裂。**
>
> 撕裂只取决于两件事：**缓冲是否分离**、**翻页时机**。和多主争抢 DDR 无关。

## 8. 索引色（索引色 / 调色板）🔧

### 8.1 是什么

| | 像素存什么 | 颜色在哪 | 64×64 tile 大小 |
|---|---|---|---|
| **真彩色** | 颜色本身 | 就在像素里 | ARGB 16 KB / RGB565 8 KB |
| **索引色** | 一个**编号** | 在**调色板**里（全图共用） | **4 KB** |

索引色 = 每个像素只存"**用调色板第几号**"，颜色统一放在一张 256 项的调色板里。
（好比瓷砖上只写"7 号色"，旁边挂一张色卡，7 号是什么颜色由色卡决定。）

**硬件链路**：

```
读 tile → 得到索引 → 查调色板 → 得到 RGB → 送去合成
```

多一级很小的 BRAM 查表（256 × 24 位 = 768 B，或带 alpha 时 1 KB），延迟 1~2 拍。

### 8.2 好处

| # | 好处 |
|---|---|
| 1 | **BRAM 省 4 倍** —— 地图 tile 能放 47 个而不是 14 个 |
| 2 | **DDR 带宽省 4 倍** —— 读同样的 tile 只搬 1/4 数据 |
| 3 | **换调色板 = 整屏瞬间变色** —— 白天/黄昏/夜晚、受击闪红、冰冻变蓝，素材一个字节都不用改 |
| 4 | CPU 软渲染读的素材也小 4 倍 |

### 8.3 代价与限制

| 限制 | 说明 |
|---|---|
| 一次只能显示 **256 色** | 像素风/地图/背景够用；渐变丰富的特效不够 |
| **8 位索引没有半透明** | 只能表达"完全不透明"或"全透明（约定某索引 = 透明）" |
| 调色板的 alpha 是**按颜色**给的 | 同一索引的所有像素透明度相同；做不了"同色内逐像素不同透明度" |

**想要分档半透明**（阴影、血迹浓淡）可以用带 alpha 的调色板：
把血迹的 4 档浓度做成 4 个专用索引，调色板里给 4 个不同的 alpha → 就有渐变血迹了。

**想要连续半透明**（烟雾那种柔和渐变）→ 索引色做不到，得用真彩色贴图。

### 8.4 适用建议

| 数据 | 建议格式 |
|---|---|
| 地图 / 背景 tile（复用率高、少色） | **索引色** |
| 角色 / 特效（要半透明） | **真彩色（ARGB）** |
| 帧缓冲（DDR） | **RGB888，无 alpha**（背景永远不需要 alpha） |

- [ ] **分屏对比模式是否也用这 2 帧？**
      `渲染流程.md` §2.2/§2.6 规定 2 帧 A/B（整帧）；
      但 §1.5 又写"各自独立缓冲对 + 各自 done + 各自翻页 → 快慢解耦"。
      若左半 CPU 软渲、右半 HW 共用同一对 A/B，翻页要等两边都完成，
      CPU 慢会拖住 HW 那边 → 对比速率失真。
      **三种可能**：① 就用 2 帧，两边写同一 back 的不同半区，统一翻页；
      ② 2 帧是常规模式，分屏对比另开一对；③ 用 3 帧（`bank_switch.v` 的 FB_NUM=3）。
- [ ] **命令队列**放 DDR 还是只走 APB 寄存器（`渲染流程.md` §1.4 倾向寄存器/FIFO，"CPU 发命令不占 DDR"）
- [ ] 是否需要"一张大图测试区"（§2.6 列为可选）
- [ ] 贴图区是否需要双缓冲（CPU 换素材时加速器可能正在读）
- [ ] 全屏模式 vs 分屏模式的读出地址（分屏时一行可能来自不同基址）

## 10. 一页速查

### 10.1 地址

```
0x0000_0000  保留                      4 KB
0x0000_1000  CPU 程序/数据/栈         124 KB   ← 链接脚本锁定，不可改
0x0002_0000  堆 / 栈扩展             1.875 MB
0x0020_0000  Framebuffer A              6 MB   ← 双缓冲 front/back
0x0080_0000  Framebuffer B              6 MB
0x00E0_0000  分屏对比备用帧（2 帧）      12 MB   ← 分屏"各自独立缓冲对"用
0x01A0_0000  贴图 / 素材区              8 MB   ← CPU 开机从 Flash 搬
0x0220_0000  命令队列                 64 KB
0x0221_0000  预留                    ~238 MB
                                     ↑ 上限 0x0FFF_FFFF（256 MB）
```

**已用约 34 MB（13%）**

### 10.2 一行的读法（1920 宽，RGB888）

```
行 y 起始地址 = 帧缓冲基址 + y × 5760     （5760 = 16 × 360，行首拍相位恒为 0）

第 1 笔： +0     起，256 拍（4096 B）
第 2 笔： 切点   起，余下拍数（到 +5760 止）
          ↑ 每行 360 拍，跨 4 KB 边界一次 → 每行 2 笔
```

### 10.3 寻址公式

```
第 y 行第 x 个像素 = 帧缓冲基址 + y × 5760 + x × 3
第 y 行第 n 拍    = 帧缓冲基址 + y × 5760 + n × 16      (n = 0..359)
```

### 10.4 家底速查

```
逻辑：LUT 用 14%，BRAM 用 25%（65/256），DSP 3%，PLL 2/4
DDR ：256 MB，规划用 26 MB（10%）  → 容量不是问题，带宽才是
BRAM：剩 191 块，够放 14 个真彩 tile 或 47 个索引色 tile
Flash：8 MB，bitstream 占约 2.5 MB，剩约 4~5 MB
```
