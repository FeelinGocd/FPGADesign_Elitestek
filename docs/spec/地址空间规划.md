## 1. 三条硬约束

| # | 约束 | 出处 / 后果 |
|---|---|---|
| 1 | **所有 DDR 地址必须 < `0x1000_0000`（256 MB）** | `Axi_Mux` 地址 32 位 → DDR3 从口 28 位，高 4 位被丢弃，超出会回卷 |
| 2 | **一笔 AXI 突发不得跨 4 KB 边界** | AXI4 协议硬规矩，违反则从机行为未定义 |
| 3 | **CPU 写完的内存，在别人读它之前必须刷 D-cache** | CPU 有 4 KB 1-way D-cache（64 B/行），别的设备看不见它 |

| **DDR 窗口** | `0x0000_1000` 起 | 声明 `0xe000_0000`，**实际 256 MB** | 主存 + 帧缓冲 |

## 3. DDR3 分区表

按 `README.md` 的五项：Framebuffer A/B、贴图区、命令队列、堆栈。

| 区域 | 起始 | 结束 | 大小 | 写者 | 读者 |
|---|---|---|---|---|---|
| 保留空洞 | `0x0000_0000` | `0x0000_0FFF` | 4 KB | — | — |
| **CPU 程序/数据/栈** | `0x0000_1000` | `0x0001_FFFF` | 124 KB ✅ | CPU | CPU |
| **命令队列** | `0x0002_0000` | `0x0002_FFFF` | 64 KB | CPU | 加速器 |
| **堆 / 栈扩展** | `0x0003_0000` | `0x001F_FFFF` | 1.81 MB | CPU | CPU |
| **Framebuffer A** | `0x0020_0000` | `0x007F_FFFF` | **6 MB** | 加速器 / CPU | 显示读出器 |
| **Framebuffer B** | `0x0080_0000` | `0x00DF_FFFF` | **6 MB** | 加速器 / CPU | 显示读出器 |
| **分屏对比备用帧**（2 帧） | `0x00E0_0000` | `0x019F_FFFF` | **12 MB** | 左半 CPU / 右半加速器 | 各自读出 |
| **素材区**（唯一可变区） | `0x01A0_0000` | `0x0FFF_FFFF` | 上限 ~230 MB | CPU（开机从 Flash 装） | 加速器 / CPU |

**固定占用约 26 MB（10%）**，加上素材的实际用量 —— 容量依然不是瓶颈，**瓶颈在 §7 的带宽**。

> **注 1**：`0x0008_0000`（512 KB）与 `0x0200_0000`（32 MB）是官方 BSP 里以太网 DMA 缓冲的默认位置
> （`ethernetif.c` 的 `mem` / `memtx`）。本工程未启用 TSE，但仍建议避开，便于以后借用 BSP 代码。
> **注 2**：`总线逻辑.md` §9 要求"CPU 程序/数据与帧缓冲分 DDR 区" —— 本表里 CPU 段在 `0x0003_0000` 以下，
> 帧缓冲从 `0x0020_0000` 开始，中间隔了 1.81 MB，满足这条。
>
> **注 3（2026-09-16 已重排）**：帧缓冲改为 **RGB888（3 字节/像素）** 后每帧只需 **约 6 MB**，
> 原表的 9 MB/帧（XRGB8888 时代）已作废，本表已按 6 MB 重排。
> 另新增「分屏对比备用帧」12 MB，为分屏"各自独立缓冲对"预留（见 §9 待定）。

> **注 4（2026-09-21 已重排）**：**素材区是这张表里唯一会变大的区域**。
> 素材数量按演示需要增减，它就不能夹在两个固定区中间 —— 原表把「命令队列」放在 `0x0220_0000`
> （正好是 8 MB 素材区的正后方），素材一旦超过 8 MB 就直接压到命令队列上。
> 本次把 64 KB 的命令队列挪到低位 `0x0002_0000`，素材区改为从 `0x01A0_0000` 一直长到 DDR 顶端（256 MB 上限）。
> 这样**以后加素材只改 Flash 的烧录内容，这张表一个字都不用动**。
> 命令队列放低位还有个好处：它是固定小结构（CPU 写、加速器读），紧挨着 CPU 段，缓存行为好推断。

## 4. 帧缓冲布局

### 4.1 行跨距取 5760（= 行宽，不补齐）

1920 像素 × **3 字节**（RGB888）= **5760 字节/行**。

> ⚠️ **本节已按 RGB888 重写**。旧版按 XRGB8888（7680 字节/行、跨距补到 8192）编写，已作废。

**5760 是天然最优解**，因为三个整除条件同时成立：

| 性质 | 是否满足 | 说明 |
|---|---|---|
| 被 16（128bit = 一拍）整除 | ✅ 5760 = 16 × **360** | 一行正好 360 拍，无零头 |
| 被 3（1 像素）整除 | ✅ 5760 = 3 × 1920 | 行首永远是"像素 0" |
| 行首**拍相位** | ✅ 恒为 0 | 每行都从一拍的开头开始 |
| 行首**像素相位** | ✅ 恒为 0 | 每行第一个像素都从字节 0 开始 |
| 内存浪费 | ✅ **0** | 跨距 = 行宽，整帧是一整块连续数组 |

**含义：整帧就是一个"每行 360 拍"的连续数组，行与行之间没有任何空隙。** 🔧

```
第 y 行第 x 个像素 = 帧缓冲基址 + y × 5760 + x × 3
第 y 行的第 n 拍   = 帧缓冲基址 + y × 5760 + n × 16      (n = 0..359)
```

**代价**：行首地址不是 4 KB 的整数倍，4 KB 边界在行内的位置逐行漂移 🔧。
每行 5760 字节 → 最多跨 2 个 4 KB 块 → **每行 2 笔突发**（切点位置由读出器按行计算）。
若强行让行首对齐 4 KB，跨距要补到 8192，**每行浪费 2432 字节（+42%）** —— 不值得。

### 4.2 参数表（1080p，RGB888）

| 项 | 值 |
|---|---|
| 分辨率 | 1920 × 1080 ✅ |
| 每像素 | **3 字节（RGB888）** 🔧 |
| 行有效字节 | **5760** |
| 行跨距 | **5760**（= 行宽，不补齐） 🔧 |
| 每行拍数（128 位总线） | 5760 / 16 = **360 拍**（> 256 → 每行拆 2 笔） |
| 每帧字节 | 5760 × 1080 = **6,220,800 B（5.93 MB）** |
| 每帧分配 | 建议 **6 MB**（1 MB 对齐）⚠️ 待重排分区表 |
| 双帧合计 | **约 11.9 MB** |

### 4.3 640×480 调试模式

| 项 | 值 |
|---|---|
| 行有效字节 | 640 × 3 = **1920** |
| 每行拍数 | 1920 / 16 = **120 拍**（< 256 → **一行一笔**） |
| 每帧字节 | 1920 × 480 = **921,600 B（0.88 MB）** |

### 4.4 3 字节/像素带来的一个实现要点

128 bit = 16 字节，而 16 ÷ 3 = **5 个整像素 + 1 字节零头** →
从 AXI 读回来的一拍里，**像素是错位的**，需要字节级拼接才能切出一个一个 RGB888 像素。

**好消息**：因为 5760 和 1920 都能被 16 整除，**每行都从相位 0 开始，行与行之间不漂移**，
拼接的相位模式是固定循环的（每 3 拍 = 48 字节 = 16 个像素为一个循环）。

**另一个好处**：HDMI 输入就是 24 位 RGB，linebuffer 读出来**直接就能用**，不需要格式转换。

## 5. 缓存一致性（必须遵守）

### 5.1 问题

CPU 有 **4 KB 1-way D-cache（64 B/行）**，且 **没有 MMU**（`SYSTEM_CORES_0_MMU = 0`），
所以**不能靠页表把某段标成不可缓存**。

```
CPU 写 Framebuffer（软渲那部分）
   → 写停在 D-cache 里，没落到 DDR
显示读出器从 DDR 读
   → 屏幕上这部分不更新
```

注意方向：**不是"谁读到了旧数据"，而是"CPU 写的像素根本没到 DDR，而屏幕是从 DDR 读的"。**

### 5.2 解法：通知别人之前刷 cache

BSP 里已有现成实现（`app/lwip/user/arch/ethernetif.c:73`）：

```c
void flush_data_cache(){
    asm(".word(0x500F)");   // VexRiscv 自定义指令：刷 D-cache
}
```

| # | 场合 | 时机 |
|---|---|---|
| 1 | CPU 写 Framebuffer | 翻页（换 front 指针）之前 |
| 2 | CPU 装载贴图/素材 | 启动加速器之前 |
| 3 | CPU 写命令队列 | 写"启动"寄存器之前 |

### 5.3 反方向

加速器写、CPU 读 —— 本设计下 CPU 不需要读加速器写的区域，不用管。
若将来要读，读之前同样要刷。

## 6. 存储分层（四级）

| 层 | 器件 | 容量 | 来源 | 掉电 |
|---|---|---|---|---|
| **L1** 片上 BRAM | Ti60F225 内置 | **256 块 × 10 Kbit = 320 KB** ✅ | `project.res.csv` / 芯片手册 | 丢 |
| **L2** 片上小 RAM | SoC 内部 | bootloader 4 KB + OCR 8 KB ✅ | `soc.h:50` | 丢 |
| **L3** DDR3 | 板载 x16 DDR3 | **256 MB**（28 位地址封顶）✅ | `ddr3_parameter.vh` `AXI_ADDR_WIDTH=28` | 丢 |
| **L4** SPI Flash | GD25LQ64 | **8 MB** ✅ | 开发板说明书 §七 | **保存** |

> ⚠️ **常见笔误**：板载 Flash 是 **8 MB**（GD25LQ64 的 64 是 **64 Mbit**），不是 64 KB。

### 6.1 各层的性格（决定数据怎么分）

| 层 | 带宽 | 随机访问 | 定位 |
|---|---|---|---|
| **BRAM** | 极高（多端口，100 MHz 下单口 128 bit/拍） | ✅ 单周期 | **热点数据** |
| **DDR3** | 1.6 GB/s 理论，**实际 1.0~1.2 GB/s（读写共享）** | ⚠️ 几十拍延迟 | **大容量工作区** |
| **Flash** | 串行，几十 MB/s 级 | ❌ 需发命令+地址+dummy | **只做仓库，开机搬一次** |

### 6.2 BRAM 现状（256 块）✅

| 用途 | 块数 |
|---|---|
| **SoC（RISC-V）** | **43** |
| ├ DDR 跨时钟 FIFO | 17 |
| ├ CPU 的 I-cache / D-cache | 12 |
| └ 命令/响应队列 + bootloader RAM | 14 |
| **DDR3 控制器** | **22** |
| **`Axi_Mux`** | **0**（互联几乎不要钱：216 LUT / 37 FF） |
| **已用合计** | **65（25%）** |
| **剩余可用** | **191 块 ≈ 239 KB** |

**191 块能放多少 tile：**

| tile 格式 | 一个占 | 能放 |
|---|---|---|
| 64×64 ARGB8888 | 16 KB | 约 **14** 个 |
| 64×64 RGB565 | 8 KB | 约 **27** 个 |
| **64×64 索引色（8bpp）** | **4 KB** | **约 47 个** |

> 索引色见 §8。另外 linebuffer 还要占 9~12 块。

### 6.3 数据放哪：三条判据 🔧

| 判据 | 放哪 |
|---|---|
| **小而热**：每帧被复用很多次 | **BRAM** |
| **大而冷**：尺寸大，或一帧只读一次 | **DDR**（开机从 Flash 搬） |
| **要掉电保存** | **Flash** |

**Flash 不能当运行时存储用**：SPI 是串行接口、没有随机访问，读一个像素要先发命令+地址+dummy。
所以 Flash 只在**开机时搬一次**到 DDR，运行时不碰。

### 6.4 Flash 布局（实测 ✅，2026-09-21 定稿）

板载 GD25LQ64 = **8 MB**（`0x000000`–`0x7FFFFF`）。分三段，**素材永远放最后一段**：

| 段 | 起始 | 长度 | 烧录文件 | 备注 |
|---|---|---|---|---|
| bitstream | `0x000000` | 实测 **1.90 MB**，按 3.5 MB 预留到 `0x37FFFF` | `project.bit` | Efinity 生成 |
| app | `0x380000` | **固定 124 KB**（到 `0x39EFFF`） | `project.hex` | 见下方"为什么是定长" |
| 素材 | `0x3C0000` | **4.25 MB**（到 `0x7FFFFF`） | 素材 blob | 表头 + 图像数据，见 §6.5 |

```
0x000000  bitstream      实测 1.90 MB（按 3.5 MB 预留）
0x380000  app            固定 124 KB
0x3A0000  ← 余量
0x3C0000  素材 blob      4.25 MB      ← 64 KB 对齐（Flash 擦除块）
0x800000  Flash 结束
```

**为什么素材起点是一次算死的常量、不会漂移**：bootloader 从 `0x0038_0000` 搬**固定 `0x01F000`（124 KB）**
到 DDR `0x0000_1000`（`bootloader/src/bootloaderConfig.h:17-19`）。拷贝长度写死，所以 app 的 Flash 占用是定长 ——
**C 代码写到多大，素材起点都是 `0x3C0000`**（当前 app 二进制只有 4 KB，远没占满）。

**为什么素材必须放最后**：它是唯一随演示需要增加的段。放最后，长多少都只动自己的尾巴，压不到别人。
起点与 app 区之间还留了 `0x3A0000`–`0x3BFFFF` 一段余量，以后单独重烧素材不用碰 bitstream 和 app。

> ⚠️ **仍要在 Efinity Programmer 里核一眼 bitstream 的实际烧录区间**：BSP 只保证 app 在 `0x380000`；
> bitstream 从 `0x000000` 起是板级惯例（实测 1.90 MB 远小于 3.5 MB 预留），但这一条没从工具配置里核实过。

> **想给素材多腾 1.5 MB**：app 偏移从 `0x380000` 挪到 `0x200000` 即可。代价是改 `USER_SOFTWARE_FLASH` 后
> **必须重新生成 SoC IP**（bootloader 住在 SoC 片上 RAM 里，是生成 IP 时灌进去的），属于动 IP，有风险。
> **不建议现在做**，只是记着有这个余量。

### 6.5 素材表（manifest）

素材区开头放一个固定格式的表头，**软件不靠编译期常量找素材**：

| 字段 | 宽度 | 说明 |
|---|---|---|
| magic | 4 B | 认表头，如 `'ASET'` |
| 版本 | 4 B | 格式变更时递增；loader 不认识的版本直接报错 |
| 条目数 | 4 B | |
| 每条：Flash 偏移 | 4 B | 绝对地址 |
| 每条：字节数 | 4 B | 搬多少 |
| 每条：宽 / 高 | 4 B | 加速器切割用 |
| 每条：格式 | 4 B | 见下表 —— **必须有**，因为索引色与 ARGB8888 并存 |
| 每条：字节序 / alpha 预乘 | 4 B | ARGB8888 落成 4 字节时 B/G/R/A 的顺序一次定死 |

| 格式编号 | 含义 | 每像素 | 用在哪 |
|---|---|---|---|
| 0 | ARGB8888 | 4 B | 人物帧 / 特效 |
| 1 | 索引色 8bpp | 1 B | 地图 / 背景 tile，配 BRAM 调色板 |
| 2 | 索引色 8bpp + RLE | 不定 | 同上，进一步压 |

**为什么用表头而不是 C 常量**：演示要烧的是一组文件（bitstream + hex + 素材 blob），
偏移写在烧录工具里、尺寸写在打包脚本里；C 代码再手抄一份，两边一定会对不上。
用表头之后，**加素材 = 重跑打包脚本 + 重烧 Flash，C 代码一行都不用改**。

> 素材是 sprite / 特效帧、不是全屏图，4.25 MB 很宽裕：64×64 ARGB8888 = 16 KB（约 270 张）、
> 96×96 = 36 KB（约 120 张）、128×128 = 64 KB（约 68 张）。

### 6.6 开机加载流程

```
上电 → bootloader：SPI 初始化 → 读 Flash 0x380000 的 124 KB → DDR 0x1000 → 跳转 userMain
     → userMain：读 Flash 0x3C0000 的表头 → 逐条 spiFlash_f2m(Flash 偏移 → DDR 素材区)
                 → 刷 D-cache → 之后运行期再也不碰 Flash
```

实现要点：

| 项 | 说明 |
|---|---|
| 搬运函数 | `spiFlash_f2m(spi, flashAddr, memAddr, size)`，第二个参数是**任意内存地址**，直接给 DDR 素材区 |
| app 能不能用 | 能。`driver/` 在编译搜索路径上（`common/standalone.mk:12`），SPI 外设 bootloader 已经 init 过 |
| **必须刷 cache** | 该函数是 **CPU 逐字节搬**（`*ram++ = spi_read(spi)`），数据先落在 D-cache。搬完不刷，最后最多 4 KB 留在 cache 没落到 DDR，加速器读到的是半个素材。用 `data_cache_invalidate_all()`（`.word(0x500F)`，实际带写回 —— 灌帧缓存用的就是它，上板已验证） |
| 速度 | 默认 `clkDivider = 2`，SCK ≈ 16 MHz，单线理论 ~2 MB/s → 4 MB 约 **2 秒**；BSP 另有 `spiFlash_f2m_dual_` / `_quad_`，四线约 **0.5 秒**（需板上 4 根数据线都连）。开机一次可接受，嫌慢就换 quad。⚠️ 这两个数是按分频估算，待上板实测 |
| 运行期按需读 Flash | **不要**。SPI 随机读一个像素要先发命令+地址+dummy，太慢。素材全部开机搬一次，运行期只读 DDR |

> **素材放 DDR 还是 BRAM**：地图/背景 tile 走「索引色存 Flash → DDR → 加速器读索引 → **BRAM 调色板**查表」；
> 人物/特效走「ARGB8888 存 Flash → DDR → 加速器直接读，做 alpha 混合」。
> 两条路素材形态不同，但都归加速器消费，输出统一是 RGB888 帧缓冲（背景不需要 alpha）。
> 注意 **ARGB8888 是 4 字节/像素、帧缓冲是 3 字节/像素**，加速器读侧和写侧格式不同，写接口契约时别漏。

## 7. 带宽预算（本工程真正的瓶颈）

### 7.1 两侧理论带宽恰好配平 ✅

| 侧 | 算法 | 结果 |
|---|---|---|
| **AXI 侧** | 128 bit × 100 MHz | **1.6 GB/s** |
| **DDR3 侧** | x16 × 800 MT/s（tCK 2500 ps → CK 400 MHz → DDR 800 MT/s） | **1.6 GB/s** |

> ⚠️ **关键事实：DDR 颗粒只有一条 DQ 总线，读写不能同时进行。**
> 所以 **1.6 GB/s 是读写共享的总量，不是各 1.6**。
> AXI/MUX 层面读写是两条独立通道（可以同时跑），但到 DDR 面前要排队，
> 而且**读写换向有开销**（`tWTR` 等）。
> 实际可用按 65~75% 估：**约 1.0~1.2 GB/s（读写合计）** 🔧

### 7.2 显示读出需求（RGB888）

| | 640×480@60 | 1920×1080@60 |
|---|---|---|
| 每行字节 / 拍数 | 1920 B / **120 拍** | 5760 B / **360 拍** |
| 行周期 | 31.78 µs（3178 拍） | 14.81 µs（1481 拍） |
| **读出速率** | **55 MB/s** | **373 MB/s** |
| 占理论 1.6 GB/s | 3.5% | **23.3%** |
| 占实际 1.0 GB/s | 5.5% | **37%** |

> **关键结论：显示只需要占用读通道约 1/4 的时间**（1080p）。
> 因此"单 outstanding"带来的笔间空隙（几十拍）**完全不影响刷新** —— 余量 3 倍以上。

### 7.3 并发预算（1080p，加速器画半屏）

| 流量 | MB/s |
|---|---|
| 显示读（整帧） | 373 |
| CPU 写半屏（按 60fps 上限估） | 187 |
| 加速器写半屏 | 187 |
| 加速器读贴图（**有 tile 复用 / 片上缓存**） | **~20** |
| 加速器读贴图（**无复用，逐像素 1:1 / 大块 Block Copy**） | **~249** |
| **合计（有复用）** | **~767 → 占实际 1.0 GB/s 的 77%** |
| **合计（无复用）** | **~996 → 99%，压线** |

**结论：**
- **640×480@60：非常宽松**（约 15%）。
- **1080p@60：取决于贴图复用率。**
  - 高频 tile 驻留 BRAM / 片上缓存 → **77%，可行**
  - 逐像素从 DDR 读 → **99%，压线**
- 所以 **"高频 tile 放 BRAM"不是可选优化，而是 1080p 能否成立的前提** 🔧

### 7.4 撕裂与带宽无关

| 现象 | 长什么样 | **真正的原因** | 解法 |
|---|---|---|---|
| **撕裂** | 画面上下是不同帧，中间一条错位横线 | **显示正在读的缓冲被人写了** | **双缓冲 + 只在帧边界（vblank）翻页** |

> **带宽再紧张，只要读写的是两块不同缓冲，就不会撕裂；**
> **带宽再宽松，只要读写同一块缓冲，照样撕裂。**
>
> 撕裂只取决于两件事：**缓冲是否分离**、**翻页时机**。和多主争抢 DDR 无关。

## 8. 索引色（索引色 / 调色板）🔧

### 8.1 是什么

| | 像素存什么 | 颜色在哪 | 64×64 tile 大小 |
|---|---|---|---|
| **真彩色** | 颜色本身 | 就在像素里 | ARGB 16 KB / RGB565 8 KB |
| **索引色** | 一个**编号** | 在**调色板**里（全图共用） | **4 KB** |

索引色 = 每个像素只存"**用调色板第几号**"，颜色统一放在一张 256 项的调色板里。
（好比瓷砖上只写"7 号色"，旁边挂一张色卡，7 号是什么颜色由色卡决定。）

**硬件链路**：

```
读 tile → 得到索引 → 查调色板 → 得到 RGB → 送去合成
```

多一级很小的 BRAM 查表（256 × 24 位 = 768 B，或带 alpha 时 1 KB），延迟 1~2 拍。

### 8.2 好处

| # | 好处 |
|---|---|
| 1 | **BRAM 省 4 倍** —— 地图 tile 能放 47 个而不是 14 个 |
| 2 | **DDR 带宽省 4 倍** —— 读同样的 tile 只搬 1/4 数据 |
| 3 | **换调色板 = 整屏瞬间变色** —— 白天/黄昏/夜晚、受击闪红、冰冻变蓝，素材一个字节都不用改 |
| 4 | CPU 软渲染读的素材也小 4 倍 |

### 8.3 代价与限制

| 限制 | 说明 |
|---|---|
| 一次只能显示 **256 色** | 像素风/地图/背景够用；渐变丰富的特效不够 |
| **8 位索引没有半透明** | 只能表达"完全不透明"或"全透明（约定某索引 = 透明）" |
| 调色板的 alpha 是**按颜色**给的 | 同一索引的所有像素透明度相同；做不了"同色内逐像素不同透明度" |

**想要分档半透明**（阴影、血迹浓淡）可以用带 alpha 的调色板：
把血迹的 4 档浓度做成 4 个专用索引，调色板里给 4 个不同的 alpha → 就有渐变血迹了。

**想要连续半透明**（烟雾那种柔和渐变）→ 索引色做不到，得用真彩色贴图。

### 8.4 适用建议

| 数据 | 建议格式 |
|---|---|
| 地图 / 背景 tile（复用率高、少色） | **索引色** |
| 角色 / 特效（要半透明） | **真彩色（ARGB）** |
| 帧缓冲（DDR） | **RGB888，无 alpha**（背景永远不需要 alpha） |

## 10. 一页速查

### 10.1 地址

```
0x0000_0000  保留                      4 KB
0x0000_1000  CPU 程序/数据/栈         124 KB   ← 链接脚本锁定，不可改
0x0002_0000  命令队列                 64 KB   ← 固定小结构放低位（原在 0x0220_0000）
0x0003_0000  堆 / 栈扩展              1.81 MB
0x0020_0000  Framebuffer A              6 MB   ← 双缓冲 front/back
0x0080_0000  Framebuffer B              6 MB
0x00E0_0000  分屏对比备用帧（2 帧）      12 MB   ← 分屏"各自独立缓冲对"用
0x01A0_0000  素材区（唯一可变区）   上限 ~230 MB  ← CPU 开机从 Flash 搬
0x0FFF_FFFF                              ↑ DDR 顶端（256 MB）
```

**固定占用约 26 MB（10%），素材按需**

### 10.2 一行的读法（1920 宽，RGB888）

```
行 y 起始地址 = 帧缓冲基址 + y × 5760     （5760 = 16 × 360，行首拍相位恒为 0）

第 1 笔： +0     起，256 拍（4096 B）
第 2 笔： 切点   起，余下拍数（到 +5760 止）
          ↑ 每行 360 拍，跨 4 KB 边界一次 → 每行 2 笔
```

### 10.3 寻址公式

```
第 y 行第 x 个像素 = 帧缓冲基址 + y × 5760 + x × 3
第 y 行第 n 拍    = 帧缓冲基址 + y × 5760 + n × 16      (n = 0..359)
```

### 10.4 家底速查

```
逻辑：LUT 用 14%，BRAM 用 25%（65/256），DSP 3%，PLL 2/4
DDR ：256 MB，规划用 26 MB（10%）  → 容量不是问题，带宽才是
BRAM：剩 191 块，够放 14 个真彩 tile 或 47 个索引色 tile
Flash：8 MB = bitstream 1.90 MB + app 124 KB(定长) + 素材 4.25 MB（@0x3C0000）
```
