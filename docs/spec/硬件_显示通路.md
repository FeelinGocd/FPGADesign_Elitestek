# 硬件 · 显示通路（lineBuffer）：DDR → HDMI

> 状态：**已实现，上板验证通过**（可见窗口 1280×720@60；整链 TB `tb_lineBuffer` 的几何还停在 1080p，见 `实测数据.md` §6）。
> 上游接口（帧缓冲布局、地址约束）见 `设计总纲.md` §4；实测数字见 `实测数据.md`。
> 本文只讲显示侧的**结构、寄存器、格式、纪律**。

---

## 1. 解决什么问题

DDR 里放几块帧缓存，**FPGA 自己把像素取出来送到 HDMI**，CPU 只负责写寄存器
（定基址 / 开使能 / 交帧 / 看帧率）。整套通路跨**两个**时钟域：访存/写侧 100 MHz、像素侧 74.25 MHz。

| 时钟 | 频率 | 干什么 |
|---|---|---|
| `clk` | 100 MHz（`mem_clk` = `core_clk_feedback`） | 控制器取数、lineAligner、PingPong 写侧、AXI4 主口 |
| `clk_HDMI_x1` | **74.25 MHz** | PingPong 读侧、拆包、HDMI 时序、TMDS（720p60） |

---

## 2. 数据流

```
DDR 帧缓存
   │  AXI4 读突发（≤256 拍、不跨 4KB）
   ▼
AXI4_Master ──► bufferControler（按行取；全屏 241 拍 = 3856 字节，分屏 2×120 拍）
                     │ 写口（全屏时行首可能不是 16B 对齐）
                     ▼
            lineAligner（丢掉行首 skip 字节：241 拍 → 240 拍 = 3840 字节）
                     │ 写口（下游永远看到 240 拍/行）
                     ▼
            async_PingPongBuffer（双 bank，跨 100M ↔ 74.25M）
                     │ 读口
                     ▼
            bufferUnpacker（16 字节/拍 → 3 字节/像素）
                     │ 24bit 像素
                     ▼
            HDMI_Top（720p60 时序 + TMDS 编码）──► 显示器
```

---

## 3. 模块分工（越界就是 bug 的来源）

| 模块 | 职责 | **不**管什么 |
|---|---|---|
| `APB0_gpu2d`（总线层，例化在 `APB0_Interconnect` 里） | APB 解析 + 槽 2 两张表：显示寄存器 + 观测寄存器 | 不含任何功能逻辑 |
| `GPU2D_APBHandler`（`GPU_2D/interface/`） | 寄存器 → 有效信号：翻页索引、模式锁存、DONE 消费、帧率统计 | 不碰取数 |
| `bufferControler` | 按 `{段0,段1}` 把一行搬进 aligner（全屏 241 拍 / 分屏 2×120 拍），一行交一块 | **不知道**双缓冲 / DONE / 翻页 |
| `lineAligner` | 行首非 16B 对齐时按 `skip = addr[3:0]` 丢弃前导字节，241 拍 → 240 拍 | 不知道地址、不知道帧；只认 skip |
| `async_PingPongBuffer` | 双 bank 跨域，四相握手，读侧决定何时换块 | — |
| `bufferUnpacker` | 128 bit/拍 → 24 bit/像素 | — |
| `HDMI_Top` | 720p60 时序 + TMDS | — |
| `AXI4_Master` | AXI 读命令与数据 | — |

> ★ **`bufferUnpacker` → `HDMI_Top` 这一级（74.25 MHz 像素通路）一个字节都不动** ——
> 见 `设计总纲.md` §9 纪律 1。

## 4. 寄存器表（APB 槽 2 的显示子块，绝对地址 = `0xF8102040` + 偏移）

| 偏移 | 名字 | 读写 | 说明 |
|---|---|---|---|
| 0x2040 | ID | RO | 恒 `0x4C423031`（"LB01"），确认 APB 通路 |
| 0x2044 | FRAMEA_BASE_ACC | RW | 缓冲 A·左半（分屏时加速器画的） |
| 0x2048 | FRAMEA_BASE_CPU | RW | 缓冲 A·右半（分屏时 CPU 画的） |
| 0x204C | FRAMEB_BASE_ACC | RW | 缓冲 B·左半 |
| 0x2050 | FRAMEB_BASE_CPU | RW | 缓冲 B·右半 |
| 0x2054 | FRAMEC_FULL | RW | 全屏 C |
| 0x2058 | FRAMED_FULL | RW | 全屏 D |
| 0x205C | STATUS | RW | bit0 = ENABLE（不锁存，写 0 立即停）；bit1 = SPLIT（**帧边界才生效**） |
| 0x2060 | FPS_ACC | RO | 加速器侧帧率（交帧事件 / 秒） |
| 0x2064 | FPS_CPU | RO | CPU 侧帧率 |
| 0x2068 | DONE_CPU | W1S | 写 1 置位（CPU 交帧） |
| 0x206C | DONE_ACC | W1S | 写 1 置位（加速器交帧，也可由硬件脉冲置位） |
| 0x2070 | IRQ_FRAME_EVT | RO / W1C | 帧边界事件粘滞位（写 1 清）；事件由显示侧 Handler 送单拍置位 |
| 0x2074 | IRQ_FRAME_EN | RW | bit0 = 帧起始中断使能（`IRQ_frame` = EVT & EN，电平型） |
| 0x2078 | CKEY_COLOR | RW | **颜色键控键色** `[23:0]` = `0xRRGGBB`，**复位默认 `0x00FFFFFF`（白）**；语义见 `硬件_加速器.md` §6 |

★ **分屏两半的基址必须 16 字节对齐**，不对齐的写会被**直接丢掉**（读回还是旧值，软件据此能发现写错）。
★ **全屏 C / D 例外：允许任意字节偏移**（相机平移的位置就藏在低 4 位里）。
硬件取数时先向下对齐到 16 B，多读 1 拍（241 拍），由 `lineAligner` 丢掉前 `skip` 个字节 ⇒ 屏幕上看到的仍然是精确到像素的窗口。分屏不做这件事（两段各有自己的基址，跨段拼接语义不同）。
★ 键色**复位默认必须是白**：复位成 0 就等于"键色 = 黑"，素材里的黑色像素会被成片抠掉 —— 只能靠默认值兜住的坑。

> 槽 2 之内由 `APB0_gpu2d` 用 `PADDR[6]` 分块：`0x2000`–`0x2018` 是加速器观测表（见 `硬件_加速器.md` §8），
> `0x2040` 起是显示表（本表）。两张表在**同一个槽**里，所以"槽 2 = GPU_2D 一整块"。

## 5. 帧缓存格式（软件最容易写错的地方）

| 项 | 全屏 | 分屏半幅 |
|---|---|---|
| 宽 × 高（**可见**） | 1280 × 720 | 640 × 720 |
| 每像素 | 3 字节 | 3 字节 |
| **每行可见多少字节** | **3840**（= 1280 × 3） | **1920** |
| **每行从 DDR 取多少**（拍数） | **3856 / 241 拍**（3840 + 最长 15 B 对齐余量 + 1 拍取整） | **1920 / 120 拍** |
| **每行下一行跳多远**（行距） | **5760** | **2880** |
| 每行交给显示多少拍 | 240 | 120 |
| 物理布局占用 | 5760 × 720 = 4.15 MB | 2.07 MB |

★ **可见宽度和行距是两个数**：720p 只把可见窗口收窄了，帧缓冲的物理布局仍是 1080p 时代的跨距 5760，
所以每行后 640 个像素的地址空间空着不用（不读也不写，**不产生带宽**）。
四个数在 RTL 里分别对应 `H_ACTIVE` / `DISPLAY_LINE_BYTES` / `DISPLAY_ROW_STRIDE` / `GPU 的 LINE_BYTES`。

★ **一个像素的字节顺序是 B、G、R** —— 地址最低的那个字节是蓝。
（RTL 依据：`bufferUnpacker` 把最早到的字节放在 `pixel_data[7:0]`；
TMDS 编码器把 `[23:16]` 当红、`[15:8]` 绿、`[7:0]` 蓝。）

红蓝反了、或者整屏斜条纹，基本都是这里写错了。

## 6. 一行为什么必须拆笔

一行取 241 拍 < AXI 单笔上限 256 拍，但**一笔不得跨 4 KB 边界**，所以仍要拆。
行首在 4 KB 页内的偏移逐行漂移（5760 mod 4096 = 1664，32 行一个循环）：

| 页内偏移 | 拆法（241 拍 = 3856 字节） |
|---|---|
| 0 | **241（1 笔）**：3856 字节 < 4096，不跨页 |
| 1664 | 152 + 89（2 笔） |
| 3328 | 48 + 193（2 笔） |

> 相机平移后行首还会再低到 15 字节，读的起点是 `addr & ~15` —— 页内偏移按对齐后的地址算。

拆笔规则写成函数 `burst_of()`：`n = min(256, 到 4KB 线的拍数, 本段剩余拍数)`。
**本笔拍数在命令期间必须锁存**（AXI 要求命令期间稳定）。

全模块没有乘法器 / 除法器：行距和字节数是左移 4 位，到 4 KB 线是右移 4 位。

> ★ 加速器侧的拆笔有同一条公式，但它多一条**上板踩出来的**约束：**突发地址必须先清低 4 位**，
> 否则某笔会算成 0 拍、`WLAST` 永不发出 ⇒ 锁死整条 AXI。见 `设计总纲.md` §8.4。

## 7. 双缓冲与翻页（DONE 的规矩）

- **写 DONE = "这一块画完了，下一个帧边界切过去显示"**
- 置位：软件 W1S 写 1，或加速器硬件脉冲
- **清零：只有 handler 在帧边界翻页之后自己做，软件不许清**
- 左右两路独立：`DONE_ACC` 翻左半（全屏时翻 C↔D），`DONE_CPU` 翻右半
- 谁先画完谁先翻，另一路继续显示它原来那块
- **写 SPLIT 的那一拍，两个 DONE 一起丢掉**（它们属于旧模式）
- 索引只在帧边界翻，模式（SPLIT）也只在帧边界锁存 ⇒ 一帧之内的取数几何永远一致
- **索引跨模式保留**：全屏翻到 D 之后切分屏，左半显示的是 B·左半

★ 翻页 / 帧率这一层的复位是 `rst_hdmi_n`（= `axi_rst_n` & HDMI PLL 锁定，GPU 内再经 `ResetSync @mem_clk`）：
显示通路没活起来之前它不动。而加速器侧那份行模式锁存用的是 `rst_acc_n` —— 两份的复位域**故意不同**，
见 `设计总纲.md` §2.4。

## 8. 帧对齐：与加速器的握手

**显示 → 加速器：`lineBuffer_frame_start`**（写域单拍）

跨域做法（2026-10 起）：由 `GPU2D_DisplayCDC` 做 **request / ack 四相握手**。
mem 域把 `frame_start` 打成"请求"电平 → acc 域同步到后翻页、把新的 `mode/{段0,段1} 基址` 锁进 payload 并回"应答"
→ mem 域收到应答后用 `frame_commit` 放行下一帧首行预取（`lineBuffer.EXTERNAL_FRAME_COMMIT=1`）。
★ 旧的"toggle + 2FF + 已消费比对"只在 `EXTERNAL_FRAME_COMMIT=0`（独立 TB）时保留。
★ 不直接拿读域脉冲过 2FF 的原因仍在：写域 10 ns 才采一次，约 1/3 的帧会被整帧漏掉。

**约定（加速器侧必须遵守）**：

1. 收到 `lineBuffer_frame_start` 之后**才开始写后台缓冲** —— 那一刻显示已经切走，读写不会碰同一块；
2. 一帧画完（或一块画完）才拉 `acc_frame_done` 单拍脉冲。

**控制器侧的对应规则**：

- 开机没收到 `frame_start` 之前不取数；
- **只有"使能着的那个帧边界"才允许开始取数**（见 §11 第 3 条）；
- 取完第 719 行就**帧尾停手**，等下一个帧边界才取新帧第 0 行
  （提前取会取到旧帧内容 —— 那一刻基址还没翻）。停手不花代价：帧边界到第一个有效行有 30 行 ≈ 667 µs，取一行只要 ~5 µs。

> ★ 本节涉及的寄存器（ENABLE / SPLIT / DONE）复位用 `sys_rst`，比加速器的 `axi_rst_n` 早放行 ——
> CPU 可以在 DDR 校准完成前就写这些寄存器，靠的就是这一点。

## 9. ★ 显示相位免疫（所有显示通路必须遵守）

**背景**：显示通道每帧按**内部索引**（`acc_idx` / `cpu_idx`）在 A/B（或 C/D）两块缓冲间二选一，而这个索引：

- **软件读不到**（STATUS 里没有）；
- **重新烧 app 不会复位 FPGA** ⇒ 上一轮跑完停在哪、主循环里按过几次按键（手动翻页），都会让它跟软件的假设**差一位**。

差一位的表现：软件**一直在画"正在显示"的那块** ⇒ 写命令紧跟帧边界下发（扫描线在顶部），
方块**上半截被擦掉、还没重画扫描线就过去了** ⇒ 顶部出现"缺半截"。
**重新下载 bitstream（复位 FPGA，索引清 0）又会自己好** —— 这个"时好时坏"就是它的指纹。

**规矩**：画完后台缓冲后，**把显示基址的两个槽都写成"刚画好的那一块"**：

| 模式 | 调用 |
|---|---|
| 分屏 | `lineBuffer_setSplitBase(L, R, L, R)` |
| 全屏 | `lineBuffer_setFullBase(X, X)` |

索引取哪个都一样 ⇒ **显示哪块完全由软件决定，与开机初值无关**。代价：每帧两条 APB 写。

> ★ 规矩本身必须一直守着：STATUS 里没有暴露这个索引（软件读不到），所以只能靠"两个槽都写成同一块"。
> 想动 STATUS 布局、或者把逻辑塞进 74.25 MHz 像素通路，都得先想一遍 `设计总纲.md` §9 纪律 1。

## 10. 帧率统计

"帧率" = **每秒发生了几次交帧事件**（DONE 的 0→1），不是显示刷新率。

- 时间基准借显示场起始：数满 60 个 `frame_start` 算一秒（720p60）；
- 每个窗口边界把上一窗口的计数锁存进 `FPS_ACC` / `FPS_CPU`；
- **所以只交一次帧的话，那个 1 只在一个窗口里存在**，之后回到 0 —— 这是正常语义，不是故障（读的时候建议轮询取峰值）。

## 11. 上板踩过的四个坑（都已修 + 补了回归）

| # | 现象 | 根因 | 怎么发现的 |
|---|---|---|---|
| 1 | 块被截成 257 拍 | 一笔的拍数是组合值，命令期间会变 | 控制器 TB |
| 2 | 翻页后仍显示旧内容 | 帧边界**同拍竞争**：handler 翻索引、控制器同拍锁基址 | 整链 TB |
| 3 | 整屏每行水平错开 | **帧中间写 ENABLE** 就立刻取数，读者在"一行的中间"开始消费 | **上板** |
| 4 | 翻页完全不发生 | `DONE_ACC` **缺软件 W1S 写通路**（文档写了、代码没实现） | **上板** |

第 3 条的解法：只有"使能着的帧边界"才允许取数；使能一撤就撤销许可。
第 4 条的解法：把软件写 `0x206C`（DONE_ACC，W1S）并进交帧事件（和 CPU 那一路 0x2068 对称）。

## 12. 显示侧"不做"的两件事（留档，评审会问）

### 12.1 【B】显示侧叠加层 —— 评估后不做

**想法**：HUD 不进帧缓冲，进一块小覆盖层；显示通路读到像素时顺便判断"在不在覆盖层里、是不是透明"，是就盖上去，
做到"**HUD 永远在最上、与游戏内容完全解耦**"。

**为什么不做**：

| | 做 B | 用软件层号 + 每帧重放（现行做法） |
|---|---|---|
| 动到 74.25 MHz 像素通路 | **会**：BRAM 读 + 命中比较 + mux 都插在 `bufferUnpacker` → `HDMI_Top` 之间 | **一个字节都不动** |
| 时序风险 | HDMI TMDS 必须分秒不差；工程**没有 SDC**，综合器不会帮我们约束这一级 | 无 |
| 布局风险 | 又多给综合器一次重排机会 | 无 |
| 收益 | HUD 不占帧缓冲、每帧零代价 | **HUD 自由度已经拿到了**（层号 + 每帧重放） |
| 代价 | 中 + 上面两个风险 | 每帧几条命令 |

⇒ **收益已经被软件方案拿到，代价却是动最脆弱的那条路径 —— 不做。**（软件做法见 `软件_驱动与API.md` §5）

留档要点（哪天真要做）：覆盖层放**片上 BRAM**（8bpp 索引，复用现有调色板，128×48 = 6144 B）而不是 DDR
（整条 1280 宽的带子 = 30 MB/s 额外读；只覆盖用到的小块才 ~0.4 MB/s，但那要显示通路支持行内段读）；
透明度复用 ck 语义（等于键色 = 不盖）；更新时机是**帧边界后的消隐期**（写指令在帧边界后立刻执行，不需要自己的 FENCE）；
显示侧要加四样：坐标比较、一路小取数、查调色板、一个 mux；寄存器 `OVL_EN / OVL_POS / OVL_DATA` 从 `0x207C` 起。

### 12.2 【C】真图层（每层一块缓冲 + 显示侧合成）—— 不做

| 层数 | 显示读出（720p） | 剩余给加速器写 |
|---|---|---|
| 1（现在） | **166 MB/s** | 实测安全预算 **≈ 60 MB/s（1 MB/帧）** |
| 2 | 332 MB/s | 仍可行但没收益 ✘ |
| 3 | 498 MB/s | 开始和加速器抢读 ✘ |

⇒ **不做**。图层体系用"软件层号 + 命令顺序 + 一帧重放"表达（见 `软件_驱动与API.md` §5）；
答辩时把这张带宽账摆出来就是不做 C 的理由。

## 13. 分辨率：从 1080p 收到 720p（2026-10-17）

把可见窗口从 1920×1080 改成 **1280×720**，而**帧缓冲布局与 GPU 行跨距一个字没动**。
关键是四个数分开：

| 参数 | 值 | 谁用 |
|---|---|---|
| `H_ACTIVE` / `V_ACTIVE` | 1280 / 720 | `pixel_timing.v`（`define VIDEO_1280_720`），像素时钟 **74.25 MHz** |
| `DISPLAY_LINE_BYTES` | 3840 | 显示每行**可见**多少字节（`LINE_BYTES` 参数） |
| `FETCH_BYTES` | 3856 | 显示每行**从 DDR 取**多少（240 + 1 拍对齐余量，给 `lineAligner`） |
| `DISPLAY_ROW_STRIDE` | 5760 | 显示**下一行跳多远** |
| `LINE_BYTES`（GPU 侧） | 5760 | 加速器写帧缓冲的行跨距 |
| `FRAME_LINES` | 720 | 取满 720 行就帧尾停手 |

720p 时序参数：`H_FRONT/H_SYNC/H_BACK = 110/40/220`、`V_FRONT/V_SYNC/V_BACK = 5/5/20`
⇒ 行 1650 像素、帧 750 行，74.25 MHz × 60 Hz 正好对上。

**没动的**：C/D 基地址、双缓冲切换、翻页机制、PRAM 素材、`Compositor` / `imageCombine` 的内部 1920 容量
（保留 1920 是为了不再动合成器结构，实际只写前 1280 像素）。

完整改动清单（改了哪几行）见 `_归档/分辨率调整_1280x720.md`。
