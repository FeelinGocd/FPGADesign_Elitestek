## 2. 带宽实测

### 2.1 口径

- 条件：1080p60，**显示全程开着**（扫描读一直占着读通道）；
- 计时用 GPU_2D 寄存器自报的 `BUSY_CYC`（100 MHz，1 周期 = 10 ns）；墙钟口径已在 mode 9 用 CLINT 交叉验算过；
- 写拍 × 16 字节 = 写字节数。

### 2.2 结果（2026-10-01，`LB_TEST_MODE = 12`）

| # | 负载 | 写 | 读 | 忙 | 换算 |
|---|---|---|---|---|---|
| ① | 整屏 FILL 1920×1080 | 388800 拍 = **6075 KB** | 0 拍 | **11455 µs** | 写带宽 **543 MB/s**；占帧周期（16667 µs）**69%** |
| ② | 8 个 64×64 BLIT + FENCE | 6656 拍 = 104 KB | 7168 拍 = 112 KB | **813 µs** | 脏区 98 KB 像素 → 实写 104 KB（+6%）、实读 112 KB（+14%） |

**由 ① 推出的三个决策数**

- 实测写带宽 **543 MB/s**（显示开着的最坏情况）；
- 加上显示读 373 MB/s ⇒ 总线占用 **916 MB/s ≈ 92%**（按 1.0 GB/s 口径）；
- **消隐窗（`frame_start` → 首行有效 = 41 行 = 607 µs）内最多改写 321 KB**（整屏的 5%）= 26 个 64×64 精灵（**只算写一次**）。

**由 ② 推出的结论**

- 8 个 64×64 脏区 + 帧同步 = 813 µs > 607 µs（**133%**）⇒ **"单缓冲 + 消隐窗"不成立**（上限约 6 个精灵，还不含擦旧位置）；
- 但放进双缓冲的整帧时间（16667 µs）里只占 **5%**；按"擦 + 画"3 倍算（312 KB/帧 ≈ 2.4 ms）也只占 14% ⇒ **动图走双缓冲 + 脏区，时间完全不是问题**。

### 2.3 显示侧读出（设计口径 + 理论）

| | 640×480@60 | 1920×1080@60 |
|---|---|---|
| 每行字节 / 拍数 | 1920 B / 120 拍 | 5760 B / 360 拍 |
| 读出速率 | 55 MB/s | **373 MB/s** |

DDR3 理论 1.6 GB/s（读写共享），实际可用 **1.0~1.2 GB/s**。

## 3. 命令开销（★ 这一节的数据最"半旧"，用之前先看日期）

### 3.1 已有的一次实测（2026-10-02，`demo_anim.c`）

条件：32 个 16×16 方块、全屏活动区 1920×1080、速度随机 ±2/±3 像素/帧、跑 600 帧、**命令全是 FILL**。

| 项 | 结果 |
|---|---|
| 帧率 | **60 fps**（600 帧 / 9980 ms，锁在显示帧边界上） |
| 命令数 | **64 条/帧**（32 条铺底 + 32 条画元素）+ 1 条 FENCE |
| 簇个数 | 32 个（元素分散、几乎不合并） |
| 忙时间 | **355 µs/帧**（占 16.7 ms 的 **2.1%**） |
| 自检 | 172800 个采样点，不一致 **0** |
| 元素重叠帧 | 110 / 600（z 序 + 裁剪规则被真正考到） |

⇒ **约 5.5 µs/条命令**，当时是**命令开销主导**（这一帧只写了约 100 KB ≈ 280 MB/s，远低于 543 MB/s 的实测上限）。
**含义：元素越碎、命令越多，瓶颈越早出现** —— 加压要按"命令数"画阶梯。

### 3.2 ⚠️ 这份数据不能直接外推

那次测的全是 **FILL**（28×28 铺底 + 16×16 元素）。之后的硬件变了：多了 PRAM 精灵源、多了 alpha 混合
（alpha 每条命令**多一次 DDR 读回**）。⇒ **每条命令的开销结构已经不同，不能用 5.5 µs 去推"元素数上限"。**

### 3.3 待补的基线测量（半天，不改 RTL、不改素材）

| # | 量什么 | 怎么量 |
|---|---|---|
| 1 | 同尺寸下 `FILL` / `sprite` / `spriteCK` / `spriteAlpha` 各自的耗时 | 固定 w×h（如 16×16 / 32×32 / 64×64）各发 N 条，读 `BUSY_CYC` 差值与命令计数差值 |
| 2 | 耗时 ~ 行数 / 面积的曲线 | 同一命令扫 h（4 / 8 / 16 / 32 / 64 行） |
| 3 | **满屏元素都在动**时脏区方案的命令数 / 忙时间 / 写字节 | 元素数阶梯加压（配合赛题高阶第 3 条） |

有了 1、2 才能说"元素数极限在哪、卡在命令还是带宽"；这三条本身就是报告里最有分量的图。

### 3.4 CPU 侧的已知账

| 项 | 值 | 口径 |
|---|---|---|
| 一条命令 = 2 条 CI | 约 **20 拍/CI** | 按 `-O0` 估 |
| 半屏背景 1020 个 tile | ≈ 2040 条 CI ≈ **408 µs/帧** ≈ 2.4% CPU | 同上（v1 的"CPU 展开 tile"方案） |
| CPU 自己写帧缓冲 | **~17 MB/s** | 上板实测（逐像素写 DDR） |
| 半屏 1080p 一帧 = 3.1 MB | ⇒ **FPS_CPU ≈ 5** | 与 mode 6、分屏对比实测一致 |

**TB 侧踩过的坑（写新 TB 时照做）**

1. **调色板参考数组必须 32 位**（`reg [31:0] pal [0:255]`）—— 文件是 8 位十六进制，按 24 位读会让 `$readmemh` 丢值 ⇒ 那一项是 X，症状是"期望值全 X、满屏不一致"，看着像 RTL 坏了（**踩过 3 次**）；
2. **运行目录里的 `palette.hex` / `assets.hex` 要跟着 `res/func/output/` 更新** —— TB 的 DUT 读运行目录、参考读 output，两份不一样会报一堆假错；
3. **从机模型必须查 `WLAST` 落在 `AWLEN` 定的那一拍** —— 只按 `AWLEN` 数拍的模型，"说好 256 拍只来 34 拍"不报任何错（这就是当初漏掉拆笔死锁的原因）；
4. **必须有一条"逐字节比绝对内容"的用例** —— 只比"两遍一致 + 掩码"查不出常数色被转反这类错。

| 5 | 纯色层那格带的是**颜色不是地址**，`CmdExec` 却按行递推 | 第 2 行起颜色就变（闪红一行一个色） |
| 6 | `imageCombine` 的 `case` 里 `S_COMBINE` 写了**两遍** | 仿真取第一个、综合工具不一定 —— 这种"仿真过板上不对"的坑不留 |

**★ 这里最值得记的一条方法论**：这 6 个里有 5 个**端到端 TB 一跑就现形**（卡住 = `line_done` 数不够，数据错 = 逐字节比对），
而**板上的表现只有一个"卡住"** —— 从"板上卡住"到"知道是哪一级卡住"，中间全靠这条 TB。
所以**每次加像素级功能，先把端到端 TB 的那一段补上，再谈上板**。
