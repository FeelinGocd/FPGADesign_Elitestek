# 功能清单（已实现能力 + 明确不做的边界）

> 用途：① 评审时一句话说清"这个加速器有什么、边界在哪"；② 答辩被问"为什么不做 XX"时直接照这张表答。
> **只写已经在这份 RTL 里的能力和已经定死的取舍**；未实现的功能不进本文（要加功能先讨论，讨论完先改 RTL 再回来改这张表）。
> 工作量口径（当年估的）：小 = 1 天内 / 中 = 2~4 天 / 大 = 1 周以上（含仿真与上板）。

---

## 1. 已实现能力

| 能力 | 命令 / 接口 | 挂在哪一层 | 备注 |
|---|---|---|---|
| **纯色填充 FILL** | `funct3=1` | `cmd/CmdExec.v` + 合成器常数色 | 任意 `w×h` |
| **块拷贝 BLIT**（DDR → DDR） | `funct3=2`，`SRC=0` | 读通路 + 行缓冲 + 合成器 | 源与目的同跨距 |
| **片上素材精灵** | `funct3=2`，`SRC=1` | `pixel/palette/*`（PRAM，**零 DDR 读**） | 命令只带字偏移 |
| **颜色键控 ck** | `flags[4]`，键色走 APB `0x2078` | `process/colorKey.v` + 掩码通路 | 默认键色白 |
| **X / Y 镜像** | `flags[6:5]` | `CmdExec` + `PaletteSource` + `PaletteDecoder` | MX 只对 PRAM 源；MY 两条源都行 |
| **90° 旋转** | `flags[7]`（由 `param[23]` 搭上来） | `CmdExec` 的按列地址 + `PaletteSource` 的 `R_REQ/R_WAIT/R_OUT` | 吞吐降到约 1/4；旋转时屏蔽 MX |
| **硬件 Alpha 混合（逐像素 α）** | `MODE=2` | `process/alphaBlending.v` | **12 个 DSP**；α 在调色板高字节 |
| **图片合成** | 3 条 CI 的合成命令，第 2 层 `flags[2:0]=1` | `process/imageCombine.v` + `factory/Compositor.v` | 2 张 PRAM 图逐字节选层 |
| **颜色合成 / 色调** | 第 2 层 `flags[2:0]=3`（纯色层） | `process/imageCombine.v` 逐字节一级 | 插值染色 / 加光 / 乘系数 / 正片叠底，**12 个 DSP**（四档 mux 共用乘法器） |
| **掩码通路** | —— | 合成器选路 → 打包器掩码兜 → `wr_strb` | ck 与 α 共用这一条路 |
| **帧结束 FENCE** | `funct3=3` | `CmdExec` + `WriteController` | 写响应收齐才算完成 |
| **双缓冲 + 帧边界翻页 + 分屏** | APB 槽 2 显示寄存器 | `GPU2D_APBHandler` + `lineBuffer/*` | 左右各一路 DONE |
| **720p60 显示通路** | —— | `lineBuffer/HDMI/*` | 74.25 MHz 像素时钟 |
| **两路帧率计数器** | APB `0x2060` / `0x2064` | 显示侧 | FPS_ACC / FPS_CPU |

> ★ **掩码通路是 ck / stencil / 混合模式的共同地基** —— 它们在结构上是同一条路的不同用法。

## 2. 明确不做（含理由，答辩直接照这张表答）

### 2.1 命令面 / 场景

| 不做 | 理由 |
|---|---|
| **Sprite 表 / Tile 命令**（硬件自己循环推进地址） | 做过对比实验：① "合成擦除 + 整个场景当一个**大矩形**画"；② 硬件 Sprite 表。两版都**不如现在**（CPU 逐元素发命令 + 脏区局部重画）快，也不再稳 —— 放弃 |
| **命令表 BULK**（描述符放 DDR，硬件自己取指） | 现在 CPU 发一条命令约 5.5 µs（FILL 口径），而一帧 16.7 ms ⇒ 上百条命令仍只占十分之一；省这点 CPU 换一套描述符取指 + 一致性同步，不划算 |
| **Tilemap 背景 / 视口偏移**（`BG_ROW` / `BG_FULL`） | 功能号预留着（见 `硬件_加速器.md` §1.2），但当前场景是"整张地板贴图 + 滚动用命令坐标表达"，用不上 |
| **画线 / 圆 / 多边形** | 能用矩形组合出来的东西不进硬件，否则每加一条命令 = 多一套状态机 + 一整套验证 |
| **缩放（最近邻 / 仿射）** | 血条 / 柱子 / 扫描线 → `fillRect` 就够；放大出场 → 预生成 2~3 档素材；透视感 → 本项目的画面用不上。而水平缩放要 UV 累加器 + 采样器（任意比例还要"可取址的行缓冲"），是这套设计里风险最高的一块 |
| **逐像素 Z 缓冲** | 带宽账：1280×720 + 16 位深度 = 每帧多读 1.8 MB、多写 1.8 MB ≈ **+216 MB/s**（1080p 时是 +240 MB/s）。而我们要的 z 序是**离散层号**，软件排序 + 画家算法已经给出正确结果 |
| **硬件事务性脏区跟踪** | 元素的生死由 C 管（谁动了、旧矩形在哪、"这块缓冲里上次画在哪"），硬件只知道"某段地址被写过"；要它表达同样的事得多出一堆寄存器和 API，而 CPU 侧合并 / 退化分支本来就便宜 |

### 2.2 混合 / 颜色

| 不做 | 理由 |
|---|---|
| **全局 α / 每精灵 α（常驻透明度）** | 逐像素 α 已经在调色板里（一个索引 = 一种 (颜色, α)）⇒ 想要整体半透明就换一组索引。再加一级常驻系数 = 再吃 12 个乘法器，收益重复 |
| **逐通道 α（R/G/B 各自一条曲线）** | 一般用不上；真要用就把三种 (颜色, α) 预先拆成三个索引 |
| **DDR 帧源的 alpha** | 要 4 字节 / 像素的源格式 ⇒ 带宽与格式两头都变。α 只支持 PRAM 精灵（子弹 / 光弹 / 光晕 / 爆炸） |
| **DDR 源的 MX（水平镜像）** | DDR 源的行缓冲是 **FIFO 型 ping-pong**（只有顺序读口、没有地址口），要做就得换成可寻址 RAM |

### 2.3 显示侧

| 不做 | 理由 |
|---|---|
| **显示侧叠加层（硬件 HUD）** | 要动 74.25 MHz 像素通路（BRAM 读 + 命中比较 + mux 全插在 `bufferUnpacker` → `HDMI_Top` 之间），而工程**没有 SDC**；收益（HUD 自由度）已经被"软件层号 + 每帧重放"拿到 |
| **真图层（每层一块缓冲 + 显示侧合成）** | 带宽：720p 单层显示读 166 MB/s，两层就 332 MB/s，再加上加速器写 —— 直接压到 DDR 实际上限；而 z 序用"层号 + 命令顺序"表达已经完全够用 |
| **调色板写口（APB 改调色板项）** | 调色板是 BRAM 初值，要可写就得加一个 APB 写口 + 与像素通路的互斥。现在的"多帧素材 + 颜色合成 `tone=2` 加光"已经把闪 / 呼吸 / 换色覆盖掉了 |

## 3. 这套设计的边界（一句话版）

> **加速器只做"把一块矩形变成确定的内容"**；内容来源只有两种（常量 = FILL、另一块内存 = BLIT），
> 像素级效果全部挂在**一条掩码通路 + 一级逐字节运算**上。凡是"能用预生成素材 / 多贴一张精灵 / 
> 软件排序"表达的效果，都不进硬件 —— 这样每加一个功能都不会变成新的一套状态机。
