## 2. 已完成的游戏和渲染工作

- 房间布局池已经接入 C 代码。普通 1×1、2×2、L 型布局使用固定房间空间，L 型按左下空缺规则处理。
- 房间切换使用 C/D/第三帧 framebuffer 和 DDR 背景恢复，保留脏区表、门区域清理和镜头移动处理。
- 人物、怪物统一使用脚下中心碰撞逻辑；这部分仍需继续观察怪物穿墙回归情况。
- Boss 已加入横向移动、上下巡游和椭圆运动池；招式数据集中在 `game/game_boss_def.c`，发射器在 `game/game_shot.c`。
- `DENSE_RINGS` 使用减速再加速的环形弹幕，实际 Boss 招式会逐圈增加活跃敌弹，不再依赖驻场合成弹幕作为正式玩法。
- 敌弹使用 alpha 裁剪后的 24×25 绘制区域，碰撞和脏区仍保留 32×32 范围，避免白边和拖影。
- 逻辑更新与显示提交已经解耦。固定更新模式用于避免显示帧等待导致的整屏顿挫；ISR 负责显示提交和计数，不直接承担完整游戏逻辑。
- 之前出现的人物、怪物拖影，门位置错乱，2×2 房间残留和 HUD 重复绘制问题已有对应修复；每次继续改动后仍要做切房、镜头移动和双/三缓冲回归。
- 道具设计器位于 `tools/item_designer/`，`items.csv` 是唯一数据源。服务器提交会生成 `pending_request.md`、差异和 C 片段；这些文件代表设计请求，不代表效果已经接入 `game_item.c`。后续增加道具时要同时核对 `game.h` 的 `ITEM_*`、`g_item_defs` 和 `game_item_apply()`。

## 5. 后续优化顺序

### 第一优先级：保持实时 tint，同时控制 C/RAM 预算

当前每颗敌弹使用实时 `spriteAlphaTintRect`，这是 tint 展示功能，必须保留，不替换为预着色素材。性能优化优先从 C/RAM 常驻数据和渲染队列结构入手，敌弹数量仍按 356 槽 / 324 敌弹上限验证。

素材变更必须完整执行：

```text
res/pic → tools/img2hex/pic2pram.py → hex/assets.hex/palette.hex
→ peripheral/APB0/gpu2d/assets_desc.h → 重新编译
```

不要手写资产 ID，始终使用生成的 `ASSET_*` 符号，并运行 `tools/img2hex/check_assets.py` 做源图、PRAM、描述表和 ELF 一致性检查。

### 第二优先级：减少弹幕移动时的背景恢复带宽

当前脏区恢复已经使用 DDR 横向合并复制，但高弹量时旧位置和新位置会覆盖大量地形格。可以继续做两件事：

- 在不破坏门、石头、interact 和 HUD 清理的前提下，扩大相邻 dirty run 的安全合并范围。
- 让背景恢复使用更少的长条复制，并记录 `restore_cmds`、GPU read/write 和 `fence` 的变化。

任何扩大合并范围的修改都必须回归人物、怪物、道具、门和镜头移动，避免残影。

### 第三优先级：继续压低 CPU 绘制准备时间

基数排序已经接入。后续可把活跃弹索引单独维护，减少每帧扫描完整 356 槽；同时保留空闲槽栈的 O(1) 分配。验收条件是 `draw_avg` 继续下降，且不会因索引表失同步导致弹幕不绘制或重复绘制。

### 第四优先级：重新定义 Boss 的“高弹量”目标

当前 356 槽可以保留，正式招式可按观感选择 256、288 或 324 发。建议把目标分成两个档位：

- 实战档：保持用户确认的观感和稳定 60 FPS。
- 压测档：允许 300 以上活跃敌弹，用来验证 GPU 和 DDR 的极限，不作为默认 Boss 招式。

## 6. 当前已知边界

- 诊断构建会增加 RAM 占用和串口输出，不能把诊断版的 FPS 直接当作正式版最终指标。
- 356 槽正式构建当前 RAM 使用 84.27%，已按目标为道具和 demo1 预留约 15% 空间。
- 背景恢复、alpha 混合和显示 fence 是三个相互影响的成本，不能只用 `cmd_frame` 判断性能。
- `GAME_BOSS_BULLET_SWEEP=1` 是驻场合成压测路径，不能用于证明真实 Boss 招式效果；真实招式必须关闭该开关后测量。
- 新增素材可能改变所有后续 `ASSET_*` 编号和 PRAM 地址，必须重新生成并做一致性检查。

## 7. 建议接手顺序

1. 用 `game_release_pool356_compact_dual_20261027.bin` 做一次正常游戏冒烟测试，确认基数排序没有改变层次顺序。
2. 保持 `GAME_BULLET_TINT=1`，在同一 324 发窗口比较渲染队列和背景恢复优化前后的 `DENSE COST`。
3. 根据 GPU busy 和 fence 的下降幅度决定是否保留 324 发实战技能。
4. 把最终实测的档位、镜像名和用户目视结果追加到本文件，再恢复无诊断的正式镜像。

## 8. 2026-10-27 继续优化记录

根据最终成品需要为道具和 demo1 预留约 15% C/RAM 空间的约束，本轮保留 356 槽总弹池、324 敌弹上限和 `GAME_BULLET_TINT=1` 实时 tint，未改用预着色敌弹。

已完成：

- 渲染队列仍为 512 项、排序仍保持 `(z, 提交顺序)` 稳定语义；队列项不再为每一项重复保存 4 字节函数指针，改为 `z + arg + callback id`，回调表最多 32 项。
- `bullet_t` 的 `active/mode/type/enemy/use8` 压到一个字节的位域，弹池容量和碰撞/绘制接口不变。
- 正式构建默认使用双缓冲（`GAME_TRIPLE_BUFFER=0`）；三缓冲仍可显式传 `GAME_TRIPLE_BUFFER=1`。
- 正式构建默认关闭地图逐格渲染缓存（`GAME_WORLD_CACHE=0`），以释放约 1.5 KB RAM；需要比较房间切换 CPU 成本时可显式打开。

正式默认构建结果：

```text
RAM: 107,008 / 126,976 B = 84.27%
余量: 15.73%
弹池: 356 槽，其中敌弹上限 324 槽
```

对照构建也已通过：`GAME_WORLD_CACHE=1` 使用 108,976 B（85.82%）；`GAME_TRIPLE_BUFFER=1 GAME_WORLD_CACHE=0` 使用 109,424 B（86.18%）。因此若最终硬件必须启用三缓冲，需要继续从常驻状态或渲染排序临时区再释放约 2.2 KB，不能通过降低弹池容量解决。

本轮只完成编译和链接验证，尚未完成 COM5 上板目视回归；正式镜像仍需按第 4 节流程采样初始房、切房、Boss 密集弹幕和 HDMI 双缓冲切换。
