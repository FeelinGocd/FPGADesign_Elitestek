## 1. ① 几何变换（硬件层面的逻辑实现）

### 1.1 旋转 —— **不做**（留档一个零成本方案）

**结论：没有用得到的地方。** 我们的画面里自机固定朝上、弹幕是圆点、敌机直接画一份朝下的美术；真正需要"整体转向"的只有图标 / 激光 / 指针这类，而那些用**多帧素材**（比如星芒转一圈画 8 帧）比做旋转更简单。

**万一要用（零 RTL）**：脚本多生成一份 90°，其余朝向靠现有的 MX / MY 组合 —— **因为 MX + MY 同时开就是 180° 旋转**，所以 PRAM 只需要存 **2 份**（`_r0` + `_r90`），不用存 4 份：

| 想要的朝向 | 怎么来 | 要多存图吗 |
|---|---|---|
| **上** | `_r0` | 原图 |
| **右** | `_r90`（顺时针 90°） | **只多存这一份** |
| **下** | `_r0` + **MX + MY** | 不用，硬件组合 |
| **左** | `_r90` + **MX + MY** | 不用 |
| 四种镜像版（对角镜像） | `_r0` / `_r90` 再单独开 MX 或 MY | 不用 |

**约定（真要用时照这个写）**：屏幕坐标、**顺时针为正**、**原图一律画成朝上**、**素材宽高都对齐到 4**（MX 要求被画那一段的宽度是 4 的倍数；对 `_r90` 来说它的"宽度"是原图的高）。

> ★ **硬件转置需要什么（留档，现在不做）**：① `CmdExec` 的列模式地址生成 + `PaletteSource` 的 4 字节拼装（每次只得到 1 个有效字节，要攒 4 次才够一拍）；② 可选把 PRAM 按行号 mod 4 分成 4 个 bank 拿回吞吐；③ w/h 互换 + 与 MX/MY 组合出 8 朝向；④ 每行读长/拍数重算；⑤ 配套 TB（四角定位 / 8 朝向 / 边界）。动的是**源侧数据通路**，风险中偏大。
> ★ **它唯一划算的时机**：素材改成**运行时从 Flash/DDR 加载**、或者"转的素材多到 PRAM 放不下 2 份"的时候。现在素材是编译期常量（BRAM 初值），**预存严格更优**。

**状态**：❌ 不进硬件；⬜ 需要时让脚本多生成一份 `_r90`（零 RTL）。

### 1.2 缩放 —— **不做**（留档代价阶梯）

| 用途 | 需要哪一档 |
|---|---|
| 血条 / 柱子伸缩、扫描线、下落的箭头 | **垂直缩放**就够（最便宜） |
| Boss 出场放大、爆炸扩散 | 水平 + 垂直**整数倍**（或者干脆画几帧不同大小的素材） |
| 道具呼吸 / 脉动 | 整数倍来回 |
| "远处小、近处大"的透视感 | 任意比例（要累加器，且源必须可取址） |

**代价阶梯**：① **垂直缩放**：只改 `CmdExec` 的行推进（`行地址 += 跨距` → 按行累加器决定"重复/跳过"），**最便宜**；② **水平整数倍**：源侧加计数器，把源像素重复 N 次；③ **水平任意比例**：源侧加**定点 UV 累加器 + 采样器**，且需要"可取址的行缓冲"（PRAM 源天然可取址；DDR 源是 FIFO 型，要先换）。

**结论（2026-10-11）：不做。** 上面那四类用途都有**零硬件**的做法：

| 用途 | 零硬件怎么做 |
|---|---|
| 血条 / 柱子伸缩、扫描线、下落箭头 | 直接 `CI_gpu2d_fillRect()` —— FILL 本来就吃任意 `w/h` |
| Boss 出场放大、爆炸扩散 | 素材预生成 2~3 档大小（和旋转那份 `_r90` 同一个思路），逐帧换图 |
| 道具呼吸 / 脉动 | 同上，或者换调色板项做明暗呼吸 |
| "远处小、近处大"的透视感 | 我们的画面（弹幕 / 角色 / UI）用不到 |

**为什么留着不做**：缩放要动**源侧数据通路**（水平缩放要 UV 累加器 + 采样器，任意比例还要"可取址的行缓冲"），
是这套设计里风险最高的一块；而收益（几种画面效果）用素材 + FILL 就能拿到。
★ 真要做时的代价阶梯与接口问题在下面留档：

- 垂直缩放 = 只改 `CmdExec` 行推进（"重复 / 跳过上一行"）；水平整数倍 = 源侧加计数器；任意比例 = UV 累加器 + 采样器（PRAM 才行）
- 参数（dx / dy）从 `color[23:0]` 高位回收；行任务要多广播"这一行要不要跳"
- 跳过源行时"不发那条行任务"要和源侧 free 逻辑对齐（谁数拍数）

## 2. ② 图层叠加（通用光效）

**目标**：**一个光效模板能套在任意素材上**（不是"给每张素材画一张发光图"）。

| 用途 | 本质 | 落在哪 | 需要新硬件吗 |
|---|---|---|---|
| **人物闪红** | 像素颜色运算（往红推 / 乘系数） | 合成级逐字节（`imageCombine`） | ✅ **已实现**（= 颜色合成 / `tone=1`，`硬件_加速器.md` §5.6） |
| **拾取高光** | 叠一张发光贴图（α 混合） | **不用改硬件**：多一条精灵命令 | 不要 |

**待讨论 / 待定**

- [ ] 模板的定义：一张贴图？一组（光斑 / 光带 / 星芒）？
- [ ] 图层顺序：叠在元素**之上**还是**之下**（影子在下、高光在上 ⇒ 需要两条命令，软件排序即可）
- [ ] 哪些效果属于"模板"（与形状无关）、哪些必须"跟着形状"（见下）
- [ ] 参数：一个模板可能要每帧改强度/偏移 ⇒ 和 ③ 共用同一套参数机制

> ★ **一条已经想清的分界**：与目标形状**无关**的光效（光斑、光带、星芒）⇒ 就是"再叠一张精灵"，**零硬件**；
> 必须**跟着形状**的效果（闪红、变暗、淡出）⇒ 运算要作用在**源② 出来的像素**上，才天然只影响精灵自己的形状。

## 4. 三类都涉及的通用问题（讨论时别忘）

1. **逐元素、逐帧的参数怎么带**：参数必须**跟着命令走**（CI 是唯一有顺序保证的通道）；位可以先从 `color[23:0]` 里回收（BLIT 那 24 位本来没用；PRAM 精灵的"源行跨距"只需 13 位），不够再用 `more` 位接一条参数 CI。
2. **合成器内部的"存储 / 处理 / 控制"三件套**：现在只有"一次运算"（α），存储是**借目的帧缓冲**凑的，控制基本是空的。
   ★ 硬约束：**片上只剩 24 块 BRAM ≈ 30 KB**（≈ 100×100 RGB888）⇒ 片上的"中间存储"这条路走不通，
   多效果只能走 **pass 模型**（读回目的 → 算 → 写回，顺序归软件）。
3. **不碰 148.5 MHz 像素通路**（工程没有 SDC，那条线只靠综合碰运气）。
