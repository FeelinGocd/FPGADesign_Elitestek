> 命令格式与硬件语义见 `硬件_加速器.md`；系统级约定见 `设计总纲.md`；实测数字见 `实测数据.md`。

## 1. 分层与缓冲模型

```
应用 / demo
   │  (1) 命令层    CI_gpu2d_*                        一条命令 = 一次绘制
   ▼
2D 加速器 GPU_2D（写 DDR）
   │  (2) 用户层    user_gpu2d_* / user_lineBuffer_*  提交 / 等待 / 翻页 / 显示开关
   ▼
显示通道 lineBuffer（读 DDR 上屏；现用现取，片上只缓存两行）
```

- **命令层**只负责"描述一次绘制"；**用户层**负责**时序与纪律**（发完等完成、翻页、显示开关）；
- 显示通道硬件按 HDMI 节拍自己读 DDR，软件只能用 enable 控制它开 / 关。

| 缓冲 | 用途 | 说明 |
|---|---|---|
| A / B | 分屏时的左右两块 | 与 C / D 互斥使用 |
| C / D | 全屏双缓冲 | **当前主用** |

- 每个缓冲 = **一整帧**（可见 1280×720，物理跨距 5760 ⇒ 实际占 5760×720 = 4.15 MB）；
- 显示读的那块叫**前台**，绘制写的那块叫**后台**；
- **翻页只发生在显示的帧边界上**（硬件在帧边界消费 DONE，软件只负责"交帧"）。

### 2.1 alpha 用法（四条规矩）

```
CI_gpu2d_spriteAlphaRect(asset_base_word, stride_word, fb_back, x, y, w, h, extra);
/* extra = 0 就是纯 alpha；可拼 GPU2D_MODE_CKEY_EN | GPU2D_FLIP_X | GPU2D_FLIP_Y */
```

```
结果 = 背景 + (精灵 − 背景) × α / 255
        └── 背景 = 【这条命令要写的那块矩形】—— 硬件自己读回来，软件不用给
        └── α    = 【调色板每一项的高 8 位】（一项 = AARRGGBB），不在参数里
```

| # | 规矩 | 为什么 |
|---|---|---|
| 1 | **α 在调色板里** ⇒ 一个索引 = 一种 (颜色, α)。画素材用**固定档位**（0/128/255），别用连续渐变 | 像素数据只有 1 字节索引，装不下 α；同色不同 α 会塌成同一项 |
| 2 | **只支持 PRAM 精灵**（`flags[3]=1`） | DDR 帧源没有 α（那要 4 字节 / 像素的源格式） |
| 3 | **别拿它刷整屏** | 读回量 = 矩形那一段；整屏读回 = 373 MB/s 额外读，直接超 DDR |
| 4 | 目的里**得先有东西**（先铺底再叠） | 读回来的就是目的现状；叠多层是可以的（后画的读回前面画的结果 = 普通画家算法） |

**和 ck 的关系**：两者可以**同时开**（`extra |= GPU2D_MODE_CKEY_EN`），硬件把两个掩码**相与** ——
ck 管"这个像素整个不写"，α 管"按比例写"。素材若全是硬边（α 只有 0 / 255），两者效果等价。

### 2.1.1 tint + alpha（MODE=4，运行时换色）

```c
CI_gpu2d_spriteAlphaTintRect(asset_base_word, stride_word, fb_back,
                             x, y, w, h,
                             0x00FF4040,   /* ARGB，A 不用 */
                             160,          /* strength 0..255 */
                             1,            /* tone: 1 插值 / 2 加光 / 3 乘系数 / 4 正片叠底 */
                             extra);       /* 同 alpha：flip / ROT90 / ck */
```

- 3 条 CI：`BLIT` + `base` + `tint`；
- base 的 ROT90 在 **base 格**，tone/strength 在 **tint 格**，互不抢 `param[23]`；
- base 的 α **完整保留**（0/128/255）：`imageCombine` 先上色，`alphaBlending` 再用 base α 和背景混合；
- 和 `combineTint` 的区别：`combineTint` 是 MODE=3 **REPLACE**，会丢掉 α=128 软边；这个走 MODE=4，软边保留；
- 典型用法：敌方 A 弹 = `ASSET_bullet_type_A_base` + 红色 tint；预染的 `bullet_type_A_enemy`
  已从素材目录删除（2026-10-22），敌方弹不再有专属素材（MODE=4 同时完成 tint 和 α 混合）。

### 2.2 颜色合成（染色 / 加光 / 闪红）

**一句话**：命令形状和 `combine` 一模一样（还是一命令 3 条 CI），只是把**第 2 格从"素材"换成"一个颜色"** ——
那第 3 条 CI 带的是 `{A,R,G,B}` 而不是素材地址（位表见 `硬件_加速器.md` §1.3.1、实现见 §5.6）。

```c
/*  底色 = 一张 PRAM 素材（base_flags 带 ck ⇒ 只染素材不透明的地方）
 *  上层 = 纯红，色调模式 1 = 插值染色，浓度 128（半浓）*/
CI_gpu2d_combineTintRect(asset_base_word, stride_word,
                         GPU2D_MODE_REPLACE | GPU2D_MODE_SPRITE | GPU2D_MODE_CKEY_EN,
                         0x00FF0000u, 128u, 1u,
                         fb, x, y, w, h);
```

| 参数 | 取值 | 说明 |
|---|---|---|
| `argb` | `0x00RRGGBB` | 上层那个颜色（A 不用） |
| `strength` | `0~255` | 浓度 = 往这个颜色偏多少；**0 = 直通**（和不开色调一个样） |
| `tone` | `0`关 / `1`插值染色 / `2`加光 / `3`乘系数 / `4`正片叠底 | 见 §2.2.1 |
| `base_flags` | 照旧 | ★ **必须带 `GPU2D_MODE_CKEY_EN`** |

**四条规矩**

| # | 规矩 | 为什么 |
|---|---|---|
| 1 | **底色那格要开 ck**（`base_flags` 带 `CKEY_EN`） | 纯色层只给"往哪个颜色偏"，"写不写"由**下层那张图的 ck 掩码**决定；不开 ck 整块矩形都会被染上色（背景一起没） |
| 2 | 想**保持朝向**就在 `base_flags` 里带 `GPU2D_FLIP_X/Y` | 镜像位是**按格**的：底图那格写了才翻（纯色层没有形状，写了没用） |
| 3 | 它是"跟着形状"的效果（闪红 / 冰冻 / 变暗） | 与形状无关的光效（光斑 / 光带 / 星芒）直接**多贴一张精灵**就行，不用这条命令 |
| 4 | **别拿它刷整屏** | 和 alpha 一样：读回 / 写入量 = 矩形那一段 |

#### 2.2.1 四种色调的式子（合成级逐字节算）

| `tone` | 像什么 | 式子（`p` = 底色字节，`C` = 颜色字节，`k` = 浓度） |
|---|---|---|
| 1 | **插值染色**（受击变红、冰冻变蓝） | `p ± \|C−p\|·k/255`（往 C 偏；k=255 基本就是 C） |
| 2 | **加光**（发光、过曝） | `min(p + C·k/255, 255)`（★ 饱和，不回绕成黑） |
| 3 | **乘系数**（整体变暗 / 变亮） | `p·k/255` |
| 4 | **正片叠底**（影子、暗角、染色） | `p·C/255` |

> ★ 除法统一用 `>>8` 近似（全工程同一口径）⇒ k=255 时结果差 1 个色阶：看不出来，但**逐像素自检要照这个口径算**
> （`tb_m2loopback` 第九段的金标准就是这么写的）。
> ★ 四种色调在 RTL 里**共用一级乘法器**（按模式 mux 乘数）⇒ 一拍 12 个字节只花 **12 个 DSP**（分成四个乘法器写要 48 个）。

**demo 里的用法（受击闪红，`game/game_player.c` / `game_bullet.c`）**：撞一下 → 连闪 3 下（每下 160ms，第 1 下白、后两下红），
浓度 k 按**时间**算（不按帧数 —— 这个 demo 的帧率会跳）；闪的期间该元素**每帧强制重画**（不然站着不动就看不到闪）。

### 2.3 旋转与「四方向」（`GPU2D_ROT90`）

**两条路，按需要选**（详见 `硬件_加速器.md` §1.6.1）：

| 路径 | 接口 | 用在哪 |
|---|---|---|
| **硬件按列取样（`ROT90`）** | `extra/flip` 里带 `GPU2D_ROT90`（= `0x4`），**再按方向叠 `FLIP_X`/`FLIP_Y`** | 要现场转、或者不想多存素材 |
| **预生成 `_up` 素材** | 命令直接指向 `<名>_up` 那张（`pic2pram.py` 预留了这条路） | ★ **当前没有任何 `_up` 素材**：子弹/门都是硬件 `ROT90`（见下面遗留 #1）；只有“方向固定 + 不想吃 1/4 吞吐”时才值得走这条 |

```c
/* ★ ROT90 单用是【转置】(out(x,y)=src(y,x))，不是旋转；w/h 由驱动自动交换 */
CI_gpu2d_spriteFlipCK(base, stride, fb, x, y, w, h, GPU2D_ROT90);                 /* 转置 */
CI_gpu2d_spriteFlipCK(base, stride, fb, x, y, w, h, GPU2D_ROT90 | GPU2D_FLIP_X);  /* 顺时针 90° */
CI_gpu2d_spriteFlipCK(base, stride, fb, x, y, w, h, GPU2D_ROT90 | GPU2D_FLIP_Y);  /* 逆时针 90° */
```

| 想要 | `extra` / `flip` 传什么 |
|---|---|
| 转置（沿主对角线镜像） | `GPU2D_ROT90` |
| **顺时针 90°** | `GPU2D_ROT90 \| GPU2D_FLIP_X` |
| **逆时针 90°** | `GPU2D_ROT90 \| GPU2D_FLIP_Y` |
| 180° | `GPU2D_FLIP_X \| GPU2D_FLIP_Y` |

> 判据：**画出来是镜像的就说明裸用了 `ROT90`**。条纹木纹、圆点子弹这类对称图形，
> 转置和旋转长得一样（1024 px 里差不到 100 px），靠「看着像」验不出来 —— 必须用带方向性的图
> （箭头 / 门 / 斜接角）。

**角色的左右：只存【朝右】一套**（`pic2pram.py` 会跳过名字带 `_left` 的图）—— 要朝左就带 `GPU2D_FLIP_X`。
省下来的 PRAM 很可观（56×72 一帧 1008 字，三套动作只存一套就省下 ~6000 字）。

★ **旋转慢约 4 倍**（一拍只取 1 个索引，攒 4 个才够一拍像素）⇒ 只用来转小图（子弹 / 图标），别转大角色。
★ 已验证：仿真逐字节 err=0（`tb_m2loopback` 第 11 段，**验的是裸 `ROT90` = 转置**），上板子弹上下方向正常。
★ `ROT90|FLIP_X` / `ROT90|FLIP_Y` 这两种组合**还没有逐字节用例**（2026-10-24，见 `硬件_加速器.md` §7）。

**四方向动画表怎么摆**（`game/game_player.c` 就是这么写的）：每个方向一张序列表 + 每一拍是否翻面，共用同一套「朝右」素材：

```c
static const int side_seq[] = { R_00_standUp, R_01_right, R_00_standUp, R_01_right, R_00_standUp };
static const u32 down_flip[] = { 0u, 0u, 0u, GPU2D_FLIP_X, 0u };   /* 朝下时靠 MX 复用同一帧 */
```

★ 注意：**旋转生效时 `PaletteDecoder` 会屏蔽 MX 的「字内反序」**，但 **MX 本身仍然有效** ——
`PaletteSource` 拿它选「这一列从下往上取」，效果就是左右翻；所以 `ROT90|FLIP_X` 才是顺时针 90°（见上表）。

### 2.4 房间贴图的 rot（设计器 ↔ 固件，2026-10-24 对齐）

地图每格 = **一个字符 + 一个 `rot`(0..3)**（`tools/map_designer` 里画，`game_layout_data.c` 里导出）。

| 字符 | 含义 | `rot` 的含义 |
|---|---|---|
| `B` / `W` | 基岩地板 / 木墙 | **顺时针 90° × rot**（木纹方向） |
| `C` / `X` / `Y` / `Z` | 角块：不翻 / 左右翻 / 上下翻 / 两次翻 | 同上，**叠在翻转之后** |
| `D` | 门（1×2 格，地图里只写一格） | **门的方向**：N=0 / E=1 / S=2 / W=3（`rot & 1` = 横门） |

**变换顺序**：先按字符翻、再按 `rot` **顺时针**转 —— 和设计器预览完全一致

## 3. 时序纪律（必须成对出现）

| 接口 | 语义 |
|---|---|
| `gpu2d_exclusive_begin()` | **关显示**，准备做一次大块绘制 |
| `gpu2d_exclusive_end(target)` | 等这批命令画完 → **再开显示**（取数从帧边界重新对齐） |

**三条硬规矩**

1. **大块绘制（整屏 / 几 MB）**：`exclusive_begin()` → 画 → `exclusive_end()`。

   原因：显示的取数是"现用现取"。DDR 被写请求占满时显示会被饿到；一饿就落后，

   而且**自己追不回来**（每行两边 1:1 前进，落后多少就永远落后多少），之后整幅画面永久错位

   （上板实测：横向错开约 520 像素）。关显示时流水线排空，再使能时取数从帧边界干净起步。

2. **每帧动画**：画后台 → `fence` + `waitFrame` → **等显示真的翻页** → 再画下一帧。

3. **永远不在正在显示的那块缓冲上画** —— 会撕裂，自检也会大面积错。


> **例外**：脏区小更新不用关显示（双缓冲下显示读的是另一块，量小也饿不到）。
> ★ 还要注意"**节拍锁 60 Hz**"：FENCE 完成只表示 DONE 置位，显示要到**下一个帧边界**才消费它。
> 软件比 60 Hz 快的话，两次 FENCE 只换来一次翻页 ⇒ 自己以为的"后台"会和显示实际播放的那块错位。
> 做法：FENCE 后轮询 `lineBuffer_getDoneAcc()` 直到回读变 0（= 已被消费），自然锁到 60 Hz。
> **上板实测踩过**：不锁时 loop 跑到 77 fps，自检成片报错。

## 5. 图层与 HUD

### 5.1 现状：z 序是显式的吗

**z 序 = 命令下发顺序**（后发的盖前面的，画家算法）。硬件**没有** z 缓冲，也不需要。
为了让"元素数组怎么摆"不影响画面，软件加了**层号 + 元素 id**：**绘制顺序 = 按 (层号升序, 元素 id 升序) 稳定排序后的顺序**。

| 层号 | 名字 | 放什么 |
|---|---|---|
| **0** | `LAYER_MAP` | 地图 / 地面 |
| 8 | `LAYER_GROUND_MARK` | 地面标记：参考线、网格、坐标尺 |
| 32 | `LAYER_PROP_BACK` | 背景物件（角色可以走到它们**前面**） |
| 64 | `LAYER_ACTOR` | 角色 / NPC / 敌机 |
| 96 | `LAYER_PROP_FRONT` | 前景物件（**挡住**角色） |
| 128 | `LAYER_FX` | 特效 / 粒子 / 弹幕 |
| 192 | `LAYER_HUD` | HUD：血条、计分、字幕 |
| 224 | `LAYER_DEBUG` | 调试覆盖：帧率、探针框 |

```
typedef struct {
    int x, y, vx, vy;   /* 位置 / 速度 */
    u32 color;          /* 颜色（或素材编号 + 帧号） */
    u8  layer;          /* ★ 层号 */
    u16 id;             /* ★ 稳定排序用，创建时分配后不改 */
} elem_t;

void layer_rebuild_order(void);   /* 按 (layer, id) 重建顺序表；元素表被打乱后必须重调 */
```

- **不能用不稳定排序**：同层元素的先后会随机变化 ⇒ 重叠画面抖动；
- **验证方法**：把元素表 **shuffle** 之后画面必须**逐像素不变**。

### 5.1.1 游戏 demo：逐元素 z（透视遮挡，2026-10-21 重构）

`game/` 这套不再"一个层一个函数"，改成**渲染队列**（`game/render_list.c`）：每个元素在提交时自己带一个 z，统一稳定排序后下发命令。

```c
rl_begin();
rl_push(Z_SCENE, scene_restore, 0);   /* 0     脏区恢复（擦旧精灵） */
game_player_submit();                 /* 1000 + 脚底 y            */
game_bullets_submit();                /* 1000 + 弹底边 y          */
game_boss_submit();                   /* 1000 + Boss 底边 y；锁血再加 Z_SHIELD */
game_item_submit();                   /* 1000 + 道具底边 y        */
hud_submit(now);                      /* 5000+ / 6000（GAME OVER） */
rl_draw_all(fb, now, buf);            /* 按 (z, 提交顺序) 排序后画 */
```

| 层 | z | 说明 |
|---|---|---|
| 场景 | `0` | 地砖 / 墙 / 门，脏区恢复就在这里 |
| 实体 | `1000 + 底边 y` | 角色 / Boss / 弹幕 / 道具，**同一把深度尺子** |
| 护盾 | `3000` | 锁血玻璃罩，盖住所有实体 |
| HUD | `5000 + 10n` | toast / 血条 / 面板 / 生命 / 小地图 / 道具池 |
| 覆盖层 | `6000` | GAME OVER 窗口 |

- **透视遮挡**：实体 z 用**底边 y**（越靠下越近）⇒ 一颗弹飞到人物脚下方就盖住人物、飞到头上就被人物盖住；弹幕、Boss、道具之间也是任意两两正确（旧代码只按"相对自机的深度"分三趟，Boss / 弹幕 / 道具之间的先后并不全对）。
- **不串层**：实体最深约 816，和护盾 3000 / HUD 5000 / 覆盖层 6000 之间留足间距；`ACTOR_Z()` 把深度夹在 `[0,1500]` 防负数。
- **稳定**：同 z 按提交顺序画（排序键带 seq），画面不会逐帧抖。
- **加元素**：在自己的 `submit()` 里 `rl_push(自己的 z, 画法, 下标)`，不用改 `game_main.c` 的排序逻辑。
- **队列**：280 项；满了丢弃并计入 `rl_dropped()`，串口 `PROBE 1s` 行末尾的 `z-drop=` 正常应恒 0。

### 5.2 HUD 怎么放（零 RTL，已实现）

**（加速器那半）做法：把 HUD 当成"层号最高的一批元素"，跟着每帧的重放画一遍。** 每帧四步：

```
① 擦全部元素的旧位置        ② info_erase()  —— 擦数字框（层 0 的背景）
③ 按 (层号, id) 画全部元素   ④ info_digits() —— 画数字（层 192，永远最后）
```

② 必须在 ③ 之前（它是背景层）；④ 必须在 ③ 之后（HUD 永远在最上）。每帧多几条命令。

| 半幅 | 游戏内容（背景 + 元素） | HUD（覆盖层） |
|---|---|---|
| **左半（加速器）** | 加速器画（CI 命令） | 加速器画：HUD 作为层 192 的元素，进入"擦全部 → 按层序重放全部"这一遍，层号最高 ⇒ **最后画**，自动压在方块上；被方块擦到也无所谓，下一帧重放会补回来 |
| **右半（CPU）** | **CPU 逐像素写**（`cpu_fill(...)`）—— 这就是"纯软件"的对照对象 | **也由加速器画**（同上，层 192），左右同款同位置 |

> ★★ **对比的口径是帧率（FPS），不是像素归属**。右半的**游戏内容 100% 由 CPU 逐像素写**；加速器只往右半写那一条 HUD（两位数字 + 它的底色框）。
> 这条是**有意的例外**，理由两条：
> ① 左右两半的数字必须**同款、同位置**才方便实时对比，而 CPU 自己画就得自带一份点阵字模（CPU 读不到 PRAM，见下）；
> ② HUD 只有两条命令、占比可忽略，而"**加速器一边画整屏内容、一边还画着 HUD，依然锁住 60 fps**"本身就是硬件加速效果的证据。
> ★ 代价与纪律：右半在**同一帧**里被两个写者碰过（CPU 先写完 + `data_cache_invalidate_all()`，加速器随后只写 HUD 那一小块）⇒ **顺序必须保证**，且除 HUD 那一小块外，加速器一个像素都不许碰右半。
> ★ CPU **读不到 PRAM**（片上 BRAM 没映射到总线）⇒ 它不能复用 PRAM 里那套 32×48 数字素材。
> 如果哪天要"绝对纯净的右半"，改法就是 CPU 自绘 5×7 / 8×8 点阵字模（C 数组，字小 + 只在数字变化时重画）；**现在不做**，记在这里备查。
> ★ **分屏对比只用方块**（不做精灵版）：CPU 要画精灵就得再存一份真彩素材到 DDR/app 里，两份素材还得同步 —— 赛题基础要求举的例子本来就是"大量方块的随机移动"，够用。

**为什么不用"背景底版"**：擦除是往旧位置盲铺底色，从 DDR 读回来只有合成结果（图层已经没了）。
用另一份背景底版 BLIT 回来虽然可行，但擦除从"只写"变成"读 + 写"，带宽直接翻倍 ⇒ 超预算。
**按层重放是正确解。**

## 6. 动图与脏区（每帧只重建变化的那几块）

### 6.1 结论先行

| 问题 | 结论 |
|---|---|
| 动图怎么做 | **双缓冲 + 脏区"局部重放"**：每帧只重建变化的那几块 |
| 为什么要脏区 | 整屏重画 = 11.46 ms/帧（占帧周期 **69%**）+ 总线 **92%**；CPU 那半就没带宽了（分屏对比会饿死 CPU） |
| 能不能只用消隐窗 | ❌ 8 个 64×64 就要 813 µs > 607 µs（**133%**），上限约 6 个 |
| 重叠怎么办 | 脏区**完全重建**（铺背景 → 按 z 序重放簇内全部元素），不是"擦 + 画" |
| z 序怎么保证 | **命令顺序**：CI 队列 FIFO，后发的画在上面 |

### 6.2 ★ 每块缓冲各记一份"上次画在哪"

双缓冲 C/D 由显示端轮流显示，绘制端每帧画"另一块" ⇒ **同一帧里两块缓冲装的不是同一帧的画面**。

如果只维护一份"上次画在哪"（比如统一用"两帧前的位置"），就等于假设"每帧严格交替"——
**这个假设一旦被打断就擦错地方**：同一块连画两次（跳帧、提前退出、整屏重建之后再画）、整屏重建之后起点不再错开。

改成**每块缓冲各记一份**之后，语义变成"**这块缓冲里，这个元素上次画在哪**"，任何时候都成立。
附带好处：**在这块缓冲里没动过的元素，一个命令都不用发**。

### 6.3 每帧三步

```
① 收集脏区
   对每个元素 i（在这块缓冲里动过的）：
       脏区 = rect(它在这块缓冲里的旧位置) ∪ rect(当前位置)，各边留 1 像素
② 合并（MERGE_GAP，默认 32）
   两个矩形相交或间距 < GAP 就并成外接矩形；反复扫到这一轮没有合并为止
   （A 挨着 B、B 挨着 C 但 A 离 C 远 ⇒ 必须多扫几轮才能保证最终互不重叠）
   面积保险：并出来超过整屏 1/4 就放弃这次合并
③ 逐个矩形整块重建
   擦整块 → 补背景（或参考线，在元素【下面】）→ 区内所有元素裁到区内按 z 序重画
```

### 6.4 两条不能破的纪律

| 纪律 | 破了会怎样 |
|---|---|
| 重画必须**裁到当前矩形内** | 元素伸到矩形外的部分会盖掉别处刚补好的内容 ⇒ 屏上竖线被顶穿（透色 / 拖影） |
| 必须**重画全**（区内全部元素），不能只补差集 | 元素每帧被啃掉一圈，几帧就没了 |

有了这两条，**矩形重叠天然安全**：后处理的矩形会把自己整块重建，结果与处理顺序无关；
重叠区最多被多写一两遍（同色，幂等）。

> ★ 等价的安全写法：**只画交集（裁剪）**（现在用的），或"整块画元素 + **外层元素（z 序）、内层簇**"。
> ❌ 不安全的是"整块画元素 + **外层簇、内层元素**"：同一个元素跨两个簇时会被重复绘制，后一次盖掉另一个簇里 z 序更高的元素。
> 仿真实测（小屏穷举对拍，场景 = 大元素横跨两簇 + 高处小元素落在其中一簇内）：外层簇 + 不裁剪 = **100 个错像素**，其余三种写法都是 0。

### 6.5 为什么用"大矩形"而不是"精确的小差集"

一次 DDR 突发的宽度 = 矩形宽度。把擦除拆成"空出来的细边"看起来省字节，实际是灾难：
一条细边只有几十字节 ⇒ **突发次数暴涨**（每行还是一次突发，但每次只搬几十字节）。
**上板实测：拆细边 ⇒ 掉帧 + 闪烁 + 下方拖影更重。**

方向是"**少换向**"而不是"少字节"：DDR3 读写总线要换向（tWTR / tRTW），
大量小突发会把显示取数那条连续读流切碎。合并成大矩形正是往这个方向走。

### 6.6 参数与模板

| 宏 | 默认 | 说明 |
|---|---|---|
| `MERGE_GAP` | 32 | 合并间距。太小 = 命令多，太大 = 白填的行多（极端情况并成整屏反而更糟） |
| `MERGE_PASS_MAX` | 8 | 合并反复扫的轮数上限 |
| `AREA_CAP` | 整屏 / 4 | 面积保险：并出来超过它就不并 |

```
for (c = 0; c < g_cur_n; c++) FILL(back, 簇c, BG);          /* 先铺全部背景 */
for (i = 0; i < ELEM_N; i++)                                 /* ★ 外层: z 序(低→高) */
    for (c = 0; c < g_cur_n; c++)                            /* 内层: 簇 */
        if (元素i ∩ 簇c ≠ ∅) draw(back, 交集, 元素i);        /* ★ 只画交集 */
FENCE;
```

**约束与依赖**

| 项 | 约束 | 原因 |
|---|---|---|
| 元素坐标 | **对齐 4 像素** | 省掉首尾遮头 / 每行多读一拍的浪费（实测小图省 33%） |
| 素材宽度 | **4 的倍数** | 行按 4 像素（一个字）打包；镜像时不会把 padding 翻到行首 |
| 画布 | **双缓冲** | 赛题基础要求；也是"脏区重建"自洽的前提 |
| 帧边界 | 命令在 **FENCE 之前**全部发完；FENCE 后**等翻页真的发生**再进下一帧 | 见 §3 的节拍锁 |
| 软件状态 | 元素表 + **每块缓冲各一份旧位置** + `back` 指示 | 就这些 |

> **历史**：早期版本用"变化集 `g_prev[]` ∪ 本帧变化"的做法（规则 1：重建区 = 本帧变化 ∪ 上一帧的变化集）。
> 它也能对，但**依赖"每帧严格交替"的隐含假设**，且必须存"变化"而不是"重建区"（存错会单调递增、每帧白填一大片）。
> 现在统一改成 §6.2 的"每块缓冲各记一份"，语义更强、不再依赖交替假设。

### 6.7 自检规范（"画对了吗"的硬证据）

**模型**：某像素该是什么颜色 = **z 序最高的、覆盖该点的元素**；没有则是背景。
（有参考线 / HUD 的场景，把它们的层号一并写进期望函数。）

**采样点（每帧都查）**

1. 每个元素的**中心 + 四角**（5 点）—— 查"该画的画了没"；
2. **每个脏区簇的中心 / 边沿** —— 查残留；
3. **两帧前的元素矩形边沿各 1 px** —— 后台里存的正是两帧前那幅，**专抓拖影**；
   ★ 只查第 1 组的话，元素自己在哪都是对的，**拖影一点都查不出来**（上板实测：修复前自检只报 2 个错，而拖影 599/600 帧都在）；
4. 若干纯背景点。

**判据**：`lineBuffer_readPixel(base, px, py) == expect(px, py)` 全部相等，**不一致数 = 0**。
（`readPixel` 返回 `0xRRGGBB`，与 FILL 传的颜色同口径。）

> ⚠️ **调试场景不要缩成"一条水平带 + 只左右走"**：那样 ① 脏区只在 x 方向变化，缺 `prev` 只体现成 4 px 的尾巴；
> ② 元素永不重叠，z 序 + 裁剪那条规则压根没被测到。**缩场景只能缩"数量"，不能缩"维度"**。

### 8.0 大房间与相机（2026-10-23 起）

普通房仍是 **1280×720 屏幕坐标**（`cam = 0`）；**Boss 房是世界 45×35 格 = 1440×1120**，房间主体是 33×25 格 = 1056×800（横长，配 16:9 屏），2 格外墙 + 普通房同款角块 + 墙内石材；左右各 6 格、上下各 5 格黑边；相机四方向跟随（160×400），显示窗口是其中一个 1280×720 的矩形，由 `cam_x / cam_y` 决定。三条不变式：

| 东西 | 坐标 | 落 fb 的方式 |
|---|---|---|
| 场景 / 实体 / 子弹 / 脏区 / 判定 | **世界坐标** | 直接写 |
| HUD / 小地图 / 道具池 / toast | **屏幕坐标** | 先 `fb = game_view_fb(fb)`，坐标不动 |
| 显示窗口 | `(cam_x, cam_y)` | `base = fb + cam_y*5760 + cam_x*3`（硬件 `lineAligner` 负责字节对齐） |

- **相机移动不重画场景**：世界内容在 framebuffer 里不动，动的只是显示基址；只有 HUD 要"搬家"。
- **HUD 搬家按缓冲各记一份**：`g.hud_cam_x[2] / hud_cam_y[2]`。双缓冲下这块缓冲两帧才画一次，相机可能已经移了两次；只用一个 `cam_prev` 会留下两道旧字。相机一动，先把**那块缓冲上次的** HUD 矩形标脏擦掉，再在新位置重画。
- **可见性两套**：`game_visible_world()`（实体：必须整块在世界缓冲内 + 与相机窗口相交）、`game_visible_screen()`（HUD）。混用会把相机窗口外的怪裁掉。
- **跟随**：死区 `CAM_DEAD_W × CAM_DEAD_H`（160×120），出死区才推，每帧最多 `CAM_MAX_STEP`(8) px，最后 clamp 到 `[0, 世界-窗口]`；换房走 `game_camera_snap()`（无过渡），整屏重铺后 `game_camera_synced()`。
- **相机必须整像素**（3 字节的倍数）：硬件能吸收"整像素 × 3 字节"带来的非 16B 对齐，但不能吸收半个像素的通道相位。
- **HUD 擦除是按 32×32 瓦片做的**：cam_y 不是 32 的倍数时，一行的脏区会跨两行瓦片，场景恢复会把相邻面板行（STAGE / DMG ...）擦掉一截。因此 game_hud_prepare_overlap() 要在 vital/飘心标脏之后，按瓦片把**被波及的相邻行**补进重画列表（只置 s_draw，不重复标脏），不能只补画"数值变了的那一行"；右侧道具池也做同样的瓦片重叠检测。g_hud_need 必须每帧清零，否则会永久处于"要刷新"状态。

### 8.1 游戏规则（2026-10-22 起）

- **玩家自动开火**：每 **14 帧**一次；只有**当前朝向的 90° 象限**里存在敌人时，才沿朝向方向直射；不会自动瞄准侧后方/背后，朝向不对就不开火。

**房间布局（随机生成，6×6 网格）**：

- 房间不再硬编码：在 6×6 网格上随机生成 **11~13 间连通房间**，起点也随机。
- 每间房渲染门时直接看**周围 4 格**：
  - 邻居格没有房间 → 墙（不画门）；
  - 邻居是普通房 → `normal`；
  - 邻居是特殊房 → 邻居的特殊门；
  - **自己是特殊房** → 本房间所有门都用本房间的特殊门。
- **特殊房 = 非普通房（ITEM / SHOP / BOSS）**；普通房 = START / EMPTY。
- **生成/自检规则**（`game_room_validate()` 启动时检查，违反会打印 `ROOM ERROR` 并拒绝启动）：
  1. 起点 1 间、道具房 1 间、商店房 1 间、Boss 房 1 间；
  2. 特殊房之间**不直接相连**、**空间 8 邻域不相邻（含斜角）**；
  3. **特殊房只能接 1 间普通房（必须是叶子）**；
  4. **Boss 房不能直接连起点房**（中间至少隔一间普通房；道具房 / 商店房可以连起点房）；
  5. **普通房可以随便相邻，也可以同时接多间特殊房** —— 每个方向看邻居类型各自渲染门即可；
  6. 所有房间必须从起点连通；
  7. **Boss 房必须是离起点最远的叶子**（4 邻域 BFS 门数最大；同距离任选）。道具 / 商店 / Boss 三间必须同时找到，且两两不 8 邻域相邻；找不到就重新生成。
- **重复回廊降权**：生成时如果下一步和上一步同方向（继续拉直），只有 **25%** 概率接受，其余 75% 强制换方向，减少重复的直走廊；极端兜底改成有 3 片叶子的 **T 形**，保证道具 / 商店 / Boss 都能放下。
- **普通房接多间特殊房是允许的**：例如同一间普通房左边是道具房、右边是商店房、下面是 Boss 房，它的门分别渲染 `accessory` / `shop` / `boss`，互不冲突；但每间特殊房自己只能有**一扇门**通普通房，且 **Boss 房的门不能开在起点房上**。
- **起始房**：没有怪、没有道具、没有奖励。
- **普通空房 / 道具房**：第一次进房生成 **2 只 slime + 1 只 bug**（slime 2 帧、3 HP；bug 4 步、2 HP）：帧 0 蹲 520~840 ms，帧 1 腾空 180 ms，起跳时实际位移 12 px 并抬升最多 6 px；**有怪时不能传送（门贴图照常渲染，玩家可以走到门口）**；清完 → 发 **0~5 coin**，可以传送。
- **锁门表现**：有怪 / Boss 还活着时，按**原版**处理：门格当木墙画，玩家不能出去；**不修改/新增门素材，也不用 `combineTint` / `fillRect`**。没有邻居格的 `D` 同样是木墙。
- **房间清理奖励**：每个非起点房间在生成时随机 **0~5 coin**；普通/道具房清怪时发；**Boss 房击破时改掉 1 个随机饰品（不再发金币）**；coin 每枚拾取 +1。
- **小怪碰撞体积 = 32×32 大方块**：覆盖 slime / bug 贴图里的全部像素；玩家子弹中心点命中这个方块即扣血，接触伤害用玩家身体矩形和它做矩形相交。
- **小怪命中闪红**：被玩家子弹打中且没死时，`hit_until = now + HIT_FLASH_MS`（120 ms）；绘制用 `spriteAlphaTintRect`（MODE=4，红色 `0x00FF2828` / 强度 180 / tone 1），保留精灵 α 软边，和玩家/Boss 的受击反馈一致。
- **COINS HUD**：左侧状态面板第 11 行（`HUD_CELLS_Y = 11`，row 10），显示当前金币；下一层保留、新一局清零。
- **可交互物持久化**：金币 / 蜘蛛网 / 石头都带 `room` 记录位置；第一次进房生成，之后重进**不重随机**，直到新一关 / 新一局。石头落点避开当前房间的金币和网；金币落点避开石头。
- **进入下一层**：先 `game_coins_reset / game_web_reset / game_stones_reset / game_shop_reset` 清空交互物状态，并**强制整屏重铺两块缓冲**；普通换房仍走 same_layout 快速路径。这样旧石头/网/金币/商店商品不会在下一层留下残影。
- **数量**：蜘蛛网每间普通房/起点房 **2~3 张**；石头普通房 **5~7 块**、**Boss 房 7~8 块**（互动对象略多）、商店 0 块。
- **道具属性模型**：`item_def_t` 里用 `item_mod_t` 保存 `hp / hp_max / lives / move_v8 / fire_every / bullet_speed / range / damage / bullet_type / triple` 的增减量；`bullet_speed` 统一作用于普通/多弹幕，`range` 普通按 32 px/点、追踪按 0.8 s/点，`triple=1` 表示增加每次发射的弹幕数量（当前三向 3 发）。拾取/商店购买统一走 `game_item_apply()` 结算。HUD 的 RANGE 显示当前 `range`。
- **道具房**：第一次进房时从 4 种道具里**随机挑 1 个**放在**房间中心**（竞技场中心 `(656,336)`，不是屏幕中心）；没拿就离开再回来还是同一个（不重掷）；拿过之后这一轮不再生成。刷新权重：**没拿过 2、拿过 1（降一半）**，所以已拿过的仍可能再出，但概率减半。
- **商店房**：每轮固定生成 **1 间**，和道具房/Boss 房一样是**只接 1 间普通房的特殊叶子**，且不和其它特殊房相邻。商品两项：**heart 5 币**（只回 1 格血，不提升 `HP_MAX`）、**随机道具 15 币**（首次进店按“拿过权重减半”随机）；价格用 **16×8 数字**；商品**无底座、无浮动**；商店内**不生成 mob / web / stone**。商品按掉落物字段保存 `active/room/x/y/type`；进出商店按 `room` 刷新/擦除贴图，位置和已买状态都保留。
- **Boss 房**：第一次进房 **Boss 满血到场中心**（竞技场中心 `(656,336)`，不是屏幕中心），**先等 1 s 再出招**（这 1 s 内 Boss 不移动、不出弹、也不吃伤害）；离开再进来会重新等 1 s，但 **不重置**当前血量/位置；Boss 房的普通房邻居能看到 boss 门。
  **Boss 还活着时，Boss 房的门照常渲染，但不能传送玩家**；击破后可以传送，并在顶部生成 exit + **1 个随机饰品**。
- **特殊房内容只生成一次**：道具房第一次进来随机 1 个，没拿就离开再回来还是同一个（不重掷）；Boss 第一次进来生成，重进不重置。
- **击破 Boss**：**不再显示 WIN**；在**房间顶部那扇门的门下 64 px**（`(640,192)`，32×32）生成 **exit**。玩家用**身体矩形**碰到 exit → 下一关：`stage + 1`、重新生成一片房间、道具/Boss 重新生成、**血量补满 3 颗心、命数保留**。

**人物碰撞体积 = 脚到眼睛的小长方形**：

- 贴图 40×56，碰撞框为 **16×32（x+12, y+24）**：从脚底到眼睛，头顶/头发不参与判定，脚参与。
- 这块同时用于：移动/门洞边界、门洞触发、道具拾取、中弹判定、Boss 瞄准（`PB_OFF_X/Y`、`PB_W/H`）。
- **石头按相对上下选边缘**：石头在上、人物在下 → 用**脚底 16×8**（`PB_FOOT_H`）；石头在下、人物在上 → 用**最上一排（眼睛）16×8**（`PB_TOP_H`）。身体可以叠进石头，只有迎面的边会挡，进/出房门时不会被身体中段卡住。
- 所以进门时头可以探进墙/门里，不会再在门口被头卡住；站在门洞里时脚和身体仍会正常触发。

**触发：身体矩形走进门洞（上/下/左/右同一套）**：

- 门洞 = 地图上 `D` 格 + 它旁边那格（竖直 32×64 / 横向 64×32）。
- 玩家**身体矩形的中心**真正进入这个矩形才换房，不是"贴住墙边"就换；
- 移动边界只把**门洞那一段墙**放行（其余墙照样挡人），所以能看见人物走进门里；
- 进门后【身体矩形中心】落在**门朝向的那一格中心点**（`cx*32+16, cy*32+16`；cx/cy 是门洞两格之后的第一格），不再按"墙内侧 8 px"贴边；不会立刻又被同一扇门吸回去。

**三种门（normal / accessory / boss）的分配规则**（`game_room_door_asset()`）：

| 当前房间 | 门贴图 |
|---|---|
| 特殊房（道具 / 商店 / Boss） | **本房间的特殊门**：道具 = `accessory`，商店 = `shop`，Boss = `boss` |
| 普通房（起始 / 空房） | 通向特殊房的门 = **目的地的特殊门**；其余 = `normal` |

> 例：空(2) 的右门 → 商店(6) ⇒ `accessory`；空(4) 的左门 → 道具(3) ⇒ `accessory`、右门 → Boss(5) ⇒ `boss`；
> 起始(0) → 空(1)、空(1) → 空(2)、空(2) → 空(4) 之间 ⇒ `normal`。
> ★ 商店目前没有单独的门贴图，和道具房共用 `accessory`；以后加 `background_door_shop` 时只改 `room_special_door()`。

> ★ **换房为什么不卡**：所有房间共用同一张地图时，`game_room_commit()` 走快速路径 ——
> 不关显示、不重铺两块 4 MB 缓冲；只把 4 扇门的**实际矩形**（含 40×64 探进墙的 4 px）标脏，
> 接下来两帧各重画一次；旧人物 / 旧 Boss / 旧弹幕交给"每块缓冲各记一份旧位置"的脏区擦掉，
> HUD 缓存作废后按行重画。
> 只有地图/旋转表真的变了才回退到"关显示 + 整屏重铺"的老路（会明显卡 20~40 ms）。
> 血条因为画在面板外面（y=0..44），额外有 3 帧 fade 负责擦除。

> ★ **串口打印**：这个 BSP 的 `bsp_printf` 只认 `%d / %x / %X / %s / %c`；
> 写 `%u` 会一路扫到格式串末尾，把后面的 `\r\n` 一起吞掉（日志就不换行）。
> 要打无符号数就 `(int)` 转一下再用 `%d`。

**阶段 Boss**：血量 300，掉到**锁血线**就锁血并切到弹幕雨，雨停才继续掉血。

| 血量 | 状态 | 出什么 |
|---|---|---|
| 300 → 200 | 普通 | 四种弹幕轮换（4 列 / 7 列 / 左右横扫 / 13 列），每 10 帧一发 |
| **200（锁血 6 秒）** | 弹幕雨 | 全屏随机 x 下落，每 2 帧一颗；**一滴血都不掉**，但子弹照样被打掉 |
| 200 → 100 | 普通 | 同上 |
| **100（锁血 6 秒）** | 弹幕雨 | 同上 |
| 100 → 0 | 击破 | 不显示 WIN；房间顶部门下 64 px 生成 exit，走进去进下一关 |

- **受击反馈**：Boss 被打中闪红 120 ms —— 用的是**颜色合成**（`tone=1` 插值染色，一条命令），不是新素材。
- **血条**：顶部居中 400×14 一条 `fillRect`，右端随血量往左缩。
- **子弹池**：当前默认 356 槽，其中 **32 槽永远留给玩家**（敌弹在总活跃数达到 324 时停止生成）——
  不然弹幕雨会把池子占满，玩家连开火都开不出来还不报错。
- **绘制顺序**：元素 → HUD。HUD 最后画，否则弹幕雨会从 y=0 落下来盖住数字。

### 8.3 键盘当手柄（串口虚拟手柄，2026-10-19）

板载只有 4 个按键，玩弹幕太难受 ⇒ 加了一条"串口收按键"的路，**不动硬件**。

**协议**（PC → 板，两字节一帧）：

| 字节 | 含义 |
|---|---|
| 0 | `0xA5` 帧头 |
| 1 | `mask`：bit0 左 / bit1 右 / bit2 下 / bit3 上 / bit4 R 重开 / bit5 B 炸弹 / bit6 P 生成 |

- **只在掩码变化时发一次**；板端收到后 `PAD_TIMEOUT = 500 ms` 内一直有效 ⇒ 不需要按固定周期刷。
- 带帧头是为了让板子自己打印的文本、或者别的串口助手发的字符不会被误当成按键。
- **500 ms 收不到就自动回落到板载按键** ⇒ 拔了线照样能玩。
- **T 键 / 串口命令 `T`**：切换无敌（无限血量，开启时补满心）；`debug0` / `debug1` 是强制开/关。
- **J + 1/2/3/4（调试传送，2026-10-23）**：按住 **J** 再按数字键，跳转到对应房间——
  `J+1` 道具房、`J+2` 商店房、`J+3` Boss 房、`J+4` 起点房。
  走的是**文本命令通道**（PC 端发 `warp1\r`..`warp4\r`），不占 6 位按键掩码；
  板端 `cmd_exec()` 收到后置请求位，主循环用 `game_room_request(cell, -1)` 落到房间中心，
  已经在目标房间时只打印 `already here` 不重复重铺。

**用**：

```
uv sync                                # 第一次：建 .venv 装依赖
uv run tools/GamePad/game_pad.py --list        # 看有哪些串口
uv run tools/GamePad/game_pad.py -p COM5       # 连上，W/A/S/D 或方向键，ESC 退出
```

工具会顺便把板子打印的 `PROBE 1s ...` 日志转发到控制台（`--quiet` 关掉）。
依赖统一放在仓库根的 **`pyproject.toml`**（`pyserial` / `pillow`），锁文件 `uv.lock` 入库；
`uv sync` 之后 `.venv` 里就有包，编辑器选这个解释器就不会再报"无法解析导入 serial"。
按键状态用 `GetAsyncKeyState` 读，**有真正的按下/松开**（不是敲一下动一步）。

实现：板端 `game/game_input.c` 的 `game_keys_read()`，主循环每帧调它一次。

### 8.2 弹道与判定（2026-10-19）

**Boss 弹幕图案表**（`game_boss.c` 里的 `patterns[]`，一行一种，全走直线）：

| 图案 | 形状 | 节奏 |
|---|---|---|
| `CIRCUIT` | 周围 **16 个方向均分** | 每 2 帧一发，32 帧转满一圈，歇 30 帧 |
| `ROT` | 一圈**前后对射**（相差 180° 的两发） | 每 3 帧一对，两臂反向转，歇 26 帧 |
| `CROSS` | 十字四发，**每轮自转 90 度**（风车十字） | 每 4 帧一发，歇 34 帧 |
| `SPREAD` | 朝下扇形七发（正负 34 度），每轮自转 22 度 | 每 3 帧一发，歇 30 帧 |
| `DOUBLE_RING` | 前后对射但**两臂速度不同**（3 / 2），内外两条环 | 每 3 帧一对，歇 26 帧 |
| `WIDE_FAN` | 半圆 13 发（约正负 100 度）横扫一片 | 每 2 帧一发，歇 32 帧 |
| `PULSE` | 八对**快弹**（45 度一发，前后各一，速度 5） | 每 6 帧一对，歇 24 帧 |

> 表里还有两个加料参数：`speed2`（twin 那发的速度，做双层环）和 `spin`（每轮把起始角度再转几格，做风车）。

> 加一种弹幕 = 在 `patterns[]` 里加一行：`{count, gap, rest, step, base, speed, twin, speed2, spin}`。
> `gap`/`rest` 就是「节奏」，`count`/`step`/`base` 是形状 —— 两件事分开调。

**五种弹道**（`bullet_t.mode`，参数全走 `vx/vy`，不需要浮点；Boss 现在只用 `MOTION_LINE`）：

| mode | 轨迹 | 参数 |
|---|---|---|
| `MOTION_LINE` | 直线 | `vx/vy` = 每帧位移 |
| `MOTION_SINE` | 蛇形（下落 + 左右摆） | `vx` = 振幅、`vy` = 下落速度 |
| `MOTION_ACCEL` | 加速下坠 | `vy` = 初速，之后每帧再快 `age/8` |
| `MOTION_SPIRAL` | 螺旋 | `vx` = 半径速度、`vy` = 每帧转几格（64 格一圈） |
| `MOTION_HOME` | 追踪（每 8 帧重新对准角色，600 帧后自毁） | —— |

图案：蛇形三连 / 12 发环形 / 追踪×2 + 左右横扫 / 双向螺旋；锁血阶段的**弹幕雨**是"加速雨 + 蛇形雨"混着下。

**判定点（★ 这是手感的关键）**

| | 判定矩形（相对贴图左上角） | 说明 |
|---|---|---|
| 角色（40×56） | `x+8, y+16, 24×34` | **头不判、脚不判**，只判身体 |
| Boss | `x+14, y+36, 52×56` | 翅膀算进去，头不算 |
| Boss 锁血时 | `x, y, 80×96` | 换成**玻璃罩**大小，子弹打在罩子上碎掉 |
| 子弹 | **只用中心点**（`x+16, y+16`） | 不用 32×32 包围盒，否则透明边也会"隔空命中" |

**发射点**：Boss 从**胸口**（`boss_y + 52`）出，不是从脚底出；角色从**身体正面** 22 px 处出，不是从包围盒边缘出。

**玻璃护盾**：锁血时把专门画的 `TheBoss_shieldUp`（80×96 的玻璃罩）叠在 Boss 身上。
半透明 ⇒ 罩住还看得见 Boss；锁血期间判定框就是这 80×96 的罩子。
**被子弹打中时罩子会亮一下**（颜色合成 `tone=2` 加光，强度 150，120 ms）。
锁血阶段 Boss 本体**不闪红**：闪红代表打中了有反馈，而这时打不掉血，只能靠罩子的亮度说话。

> 之前用 12 块 `minecraft_glass` 瓦片拼过一个方框，有了专门素材就换掉了（少 12 条 alpha 命令）。
> ★ 判定收紧之后游戏会变"好躲"（以前整条腿都能被打中），这是对的方向 —— 弹幕游戏的难度应该来自**密度和轨迹**，不是来自判定框有多大。

> ★ 2026-10-17：原 `demo_anim.c`（全屏动图 + 脏区自检）与 `demo_combine.c`（两图合成四格对照）
> **已删除** —— 功能都被游戏 demo 覆盖（动图→游戏动画、合成→角色/道具叠层），留着只占 flash。
> 它们的验证价值留在 `实测数据.md` §3.1 / §5 的历史记录里。
